# Caps audit: every fixed ceiling in ferros

Status: audit for the owner, 2026-11-23, on forge da45bfe6 (manifestus 0eb4f80, vsf c0e92f3, fgtw 7785592, fluor 1b64f9d, kete c712e07). Read only: nothing changed but this file.

The owner, 2026-11-23: "The whole design premise is unlimited and compact." And: "if I open notepad and it requests 1mb of memory and it's happy, then I go and open a video because I want to search thru the frame metadata and it malloc's 4GB of RAM, it better work."

The storage windows (the vault's 8 GiB copies, clips, rawbench, the flash log, kvault, the stem) are already in docs/ONE-VAULT.md (section 0, and section 4 points at RAM); they are listed here too (rows S0 to S7) so the table is whole, and ranked above everything else.
This audit is for the rest.

Classes:
- **REAL**: a hardware, physical or protocol limit; kept, with why.
- **SAFETY**: a bound on input someone else controls (a network peer, a USB host, a kist's words), which AGENT.md Rule 0 requires; kept, with whether its size is right.
- **GUESS**: a preset someone picked that caps legitimate use; it should become as big as needed, refused only when the device is truly out.

Commits are the first commit whose diff carries the constant at its current value (`git log -S`); where the value moved since, the earlier carve is named too.

## Summary

Rows: 69, many grouping several constants of one kind (a row with two classes counts by its first). **GUESS 45**, **SAFETY 11**, **REAL 13**.

Three root causes cover most of the GUESS rows:
- **The heap is declared, not asked for.** A std app's heap stops at a ceiling its build declares (default 32 MiB), and a no_std payload's heap is a static array in .bss because ferros_heap's allocator has no grow path at all (ferros_rt's has one: SYS_ARC). The arc's window of addresses is sized from the declaration, so the declaration is the cap.
- **Slot tables sized in advance.** Surfaces, GPU blocks, pucks, the camera's window, mailboxes, extent grants, the deck's circles, TCP connections, UDP ports: each a fixed array of N slots, each slot a fixed span of addresses, where a Vec of windows taken from a large address space would do.
- **One-shot buffers sized to today's biggest thing.** The kernel's heap (22 MiB, so a kernel-held value stops at 3 MiB), IPC messages (4096 bytes, cut silently), the grants page (one 4 KiB page: about 109 capabilities, 32 handles), the vault's export (4 MiB, values past 1 MiB left out).

### The top ten (GUESS, ranked by what the owner would hit)

Above all of these: the storage windows of ONE-VAULT.md (S0 to S7: the vault full at 8 GiB a copy with about 100 GiB idle, 205 stills refused).

0. **An app's memory is capped at a heap it declares** (M0, M1). Every std process stops at `__ferros_heap` (crates/rt/ferros.ld:31, default 32 MiB; Photon 512 MiB, Lumis 4 GiB, basecalc 64 MiB). The owner's notepad that later mallocs 4 GiB dies with "memory allocation of N bytes failed". Fix: no declared ceiling; every growing image gets a window as large as the pool, frames mapped as asked, refused only at ARC_WHY_MEMORY.
1. **ferros_heap never grows, so every no_std payload's heap is a fixed .bss array** (M2, M3). The vault process 56 MiB (its index working set and the export are built here: at 8 MiB it died rewriting Mahere's capsule), the deck (map) 4 MiB, fgtw 8 MiB (died 2026-11-17 on a 573 KB ClutchOffer), kists 4 MiB, modem 16 MiB, camera 1 MiB, pucks 2 MiB. Fix: give ferros_heap the grow path ferros_rt has (SYS_ARC ARC_GROW), drop the static heaps.
2. **The deck shows at most 16 circles: settings and 15 kists** (U0). payloads/map/src/main.rs:206 `MAX = 1 << 4`, cut silently with `.min(MAX)` (lines 2130, 2157); the display's icon cache (ICON_SLOTS 16) and the deck's fit (camera::MAX) are sized to it. The 16th kist stowed has no circle. Fix: Vecs sized by the person's kist list; the icon cache an LRU in the display's growing heap.
3. **Sixteen surfaces for the whole device, four per process, each exactly 32 MiB** (M11). Photon would not start on 2026-11-12 ("no free surface (four are in use)"); raised to 16, still a fixed table. A surface for a screen past 32 MiB at 8 bytes a pixel (a 4K external panel is 63 MiB) cannot exist. Fix: surfaces as windows taken from a large address range on demand, sized to the request.
4. **The camera's window: 512 MiB for the driver's run, 512 MiB for the view, a 1 GiB fence** (M14). About eight full 1:1 RAW10 frames (60 MiB each) in flight; a longer burst or a deeper video ring is refused. With EXTENT_GRANTS_MOST (8 recordings at once) and the clips window (S1). Fix: the run's frames on demand in a window sized from the pool; fence tables per GiB as the GPU's are.
5. **A GPU client holds at most 512 MiB, sixteen clients at most** (M12). Mahere at full detail wants 376 cells of a MiB beside its frame regions; Lumis's integrator lives at fixed offsets inside the 512 MiB (std/lumis/src/gpu.rs CAMERA_LOG 29). Fix: each block's window sized from the pool, blocks a Vec; the GPU service's per-slot page tables taken on demand.
6. **All processes share 64 GiB of addresses, each taking a power of two above its ceiling** (M5). Lumis's 4 GiB ceiling takes an 8 GiB window; eight such apps and spawns fail with "arc pool exhausted". Once the declared ceilings go (row 0) this is the next wall. Fix: widen TTBR0 to 48 bits (256 TiB) and size windows from the pool; ferros_rt's TLSF (FL_MAX_LOG2 36) to match.
7. **Sixteen TCP connections and eight UDP ports for the whole device** (N0, N1). Photon, Mahere's four loaders, fgtw, the stower and the weather puck share them; the 17th CONNECT answers "[4] no free connection", a ninth app port's datagrams are no longer kept, 64 datagrams queued in all. Fix: connection and port tables as Vecs in ip's growing heap; buffers per connection on demand (already so).
8. **The kernel's heap is 22 MiB, fixed, so a kernel-held value stops at 3 MiB** (M9, S9). An OOM in the kernel is a panic and a reset; STORE_VALUE_MAX, STAGE_MAX and every "built whole in the kernel heap" reply are sized to it. Fix: the kernel heap adds 2 MiB frames from the pool as it runs low (frames.rs already hands the kernel frames); STORE_VALUE_MAX then goes.
9. **The person's export stops at 4 MiB and leaves out every value past 1 MiB** (S10). payloads/vault/src/main.rs:1977-1978: the export is built whole in the vault's fixed heap. Stills, the made wallpaper, any large document: not in the backup an identity restores from. Fix: stream the export as a VSF document written piece by piece (it already writes a value in pieces), no whole-document buffer.

Close behind: IPC messages cut at 4096 bytes without a word (M17), the grants page's 109 capabilities (M18), 16 remembered WiFi networks with the oldest dropped silently (U4), the People page's first 32 people (U3), 64 KiB stacks for no_std payloads and 1 MiB for a std app's main thread (M10), and in Photon's own tree a 256 MiB attachment limit (N10) that caps a video sent.
