# HV — ferros hv, the live oracle under Android

The thin EL2 layer that boots stock Android at EL1 on husky and watches it from above: first a dormant pass-through, then a stage-2 map with the UFS controller trapped so Android can run for real without being able to write the boot chain, and finally the m1n1-style tracer that lets us read any register Android touches while it is alive. Decided 2026-10-17 ("Oracle. Sounds delicious."). Code: `ferros_hv/`, tool: `tools/husky-hv.sh`.

## Why

BOOT.md measured the alternatives dead: UFS power-on write protect covers only the bootloader LUs and clears on the device reset Android's own UFS driver performs at probe; the LU layout cannot be re-provisioned without erasing the bootloader; GPT attributes carry no slot state; devinfo is re-synced by ABL from the Boot LU attribute. The only place left to stand between Android and the flash is EL2. ferros already owns EL2 on this phone (ABL jumps to the kernel at EL2 once pKVM is disabled), and Android's kernel is a GKI build that boots fine at EL1 (then without KVM: AVF/Microdroid off, nothing the owner uses).

The same layer is a register oracle: every MMIO access Android makes to a trapped page is a line in a log we can read, which is how the display, camera and modem bring-ups get their ground truth without the handoff dance.

## Measured facts the design rests on (2026-10-17)

- ABL loads the `boot_a` kernel at G#8008_0000 (text_offset G#8_0000) and jumps to its first instruction at EL2 with the MMU and caches off, x0 = DTB. It accepts a kernel blob with the ARM64 header + PE stub ferros's cold image uses.
- The Linux Image in `boot_a` (6.1.124-android14, LZ4-legacy in the boot.img): 35.4 MB, `image_size` G#226_0000, header flags G#A: 4 KiB pages, **physical placement anywhere** (relocatable, KASLR on). text_offset 0.
- ABL puts the ramdisks at G#8600_0000.. (49 MB with bootconfig), DTB 460 KB (base + merged overlays), `/psci` method is SMC, `/reserved-memory` exists with ~60 children.
- DRAM: G#8000_0000–G#FFFF_FFFF and G#8_8000_0000–G#A_FFFF_FFFF (12 GiB). Android's kernel today: "CPU: All CPU(s) started at EL2", KVM IPA 40 bits, cmdline `kvm-arm.mode=protected` (pKVM disabled by `fastboot oem pkvm disable`, so KVM runs unprotected).
- Cores: MPIDR Aff1 = core number 0–8 (Aff2 cluster). PSCI from EL3 starts a core at the entry given to CPU_ON in AArch64 EL2, MMU off, x0 = context.
- The ramoops result block at G#FD60_0000 survives resets and the trip through fastboot; the next ferros boot reads it (`PREV_*`).

## Milestones

### M0 — dormant hv: Android boots and runs under it (code written 2026-10-17, untested)

`boot_a`'s kernel = `[ferros_hv flat binary, padded to G#18_0000][Linux Image]`, LZ4-legacy, mkbootimg v4 with the original (empty) ramdisk and cmdline (`tools/husky-hv.sh`). ABL loads it at G#8008_0000, so the Image sits at G#8020_0000, 2 MiB aligned as its header asks.

At entry the hv:
1. Copies itself to **HV_BASE = G#A_FC00_0000** (the last 64 MiB of DRAM; linked there, the pre-copy code is PC-relative), zeroes bss, takes a stack.
2. Rebuilds the DTB at G#A_FBF0_0000 (ordinary RAM just below, which Linux reserves itself when it reads the tree) with one node added: `/reserved-memory/hv@afc000000 { reg = <0xa 0xfc000000 0x0 0x4000000>; no-map; }`. The `reg` and `no-map` string offsets are taken from the existing strings block. Any surprise in the tree → crumb G#E1 and stop (better than letting Linux allocate over the hv).
3. Programs EL2 so EL1 sees a bare machine: HCR_EL2 = RW | TSC | APK | API | ATA (VM = 0, E2H = 0, TGE = 0, no interrupt routing to EL2); CPTR_EL2 with TFP and TZ clear (FP/SIMD and SVE through, ZCR_EL2 = max where SVE exists); MDCR_EL2 with HPMN = all counters, SPE and trace buffers owned by EL1, no debug traps; CNTHCTL_EL2 = EL1PCTEN | EL1PCEN, CNTVOFF_EL2 = 0; ICC_SRE_EL2 = G#F, ICH_HCR_EL2 = 0; VPIDR/VMPIDR = the real core; HSTR_EL2 = 0; SCTLR_EL1 = reset value; VBAR_EL2 = the hv vectors.
4. `eret` to G#8020_0000 as EL1h, DAIF masked, x0 = the new DTB, x1–x3 = 0.

Afterwards the hv runs only on **SMC traps** (TSC):
- PSCI **CPU_ON** (G#C400_0003): the target core's requested entry and context are recorded by core index, the entry is replaced with `_secondary`, the call forwarded. `_secondary` configures EL2 on the new core and erets to the recorded entry with the context EL3 delivered in x0.
- PSCI **CPU_SUSPEND** (G#C400_0001) and **SYSTEM_SUSPEND** (G#C400_000E) name a resume address too; same swap (harmless for standby states, where the call returns normally).
- Every other SMC is forwarded with x0–x17 and the results returned. HVC from EL1 gets SMCCC NOT_SUPPORTED (Linux at EL1 has no hyp stub to call).
- Any other exception at EL2 writes ESR/ELR/FAR to the report block (G#FD60_0058/60/68) with stage G#E2 and parks the core.

Crumbs: G#FD60_0040 stage (A1 entered, A2 DTB rebuilt, A3 EL2 configured, A4 eret; E1 DTB failed, E2 unexpected trap, E3 panic), +G#48 SMC count, +G#50 CPU_ON count.

**M0 passes when** Android reaches adb, `dmesg` says "CPU: All CPU(s) started at EL1", `/sys/firmware/devicetree/base/reserved-memory/hv@afc000000` exists, all nine cores come online (`/sys/devices/system/cpu/online` = 0-8), the phone suspends and wakes (screen off/on, CPU_SUSPEND resumes through `_secondary`), and `tools/husky-to-ferros.sh` brings slot b back. Restore if it does not: `fastboot flash boot_a /mnt/Harbor/tmp/husky-backup-2026-10-13/boot_a.img`. Failure to boot is self-limiting: ABL burns slot a's three retries and falls back to slot b (ferros), whose DIAG then shows the hv crumbs.

Known gaps to expect at M0: the vendor drivers that talk to pKVM (S2MPU IOMMU, power-domain `pkvm` modules) must take their "no hypervisor" path at EL1 — they did under `pkvm disable` with KVM unprotected, which is close but not identical. Pointer authentication, MTE and SVE are passed through; anything else that traps shows up as an E2 crumb with its ESR, which is exactly the information needed.

### M1 — stage 2 with an identity map and the UFS firewall

HCR_EL2.VM = 1 with VTCR_EL2 for 40-bit IPA, 4 KiB granule, a flat identity map of all DRAM and MMIO built once in the hv's 64 MiB (concatenated tables as needed), **except** the UFS host controller pages (G#1320_0000.., the HCI register block) which are unmapped so every access traps (data abort from lower EL, EC G#24, with the ISS saying load/store, width, register). The handler emulates the access against the real register and, on a doorbell write (UTRLDBR), reads the UTRD → UPIU → SCSI CDB from guest memory first: WRITE/UNMAP/FORMAT/WRITE BUFFER to LU1, LU2, LU3, or to LU0 LBAs inside `boot_b`, `vbmeta_b`, `dtbo_b`, `vendor_boot_b`, `vendor_kernel_boot_b`, `init_boot_b` and the `ferros` partition are answered with a synthetic failure (status CHECK CONDITION, data protect) without reaching the device; QUERY WRITE ATTRIBUTE bBootLunEn and SET FLAG fPowerOnWPEn / fPermanentWPEn likewise. Everything else goes through untouched. Cost: a few traps per I/O (doorbell, interrupt status, completion), microseconds each — unmeasurable against UFS latency. The GPT is read once at hv start from LU0 to know the LBA ranges.

That is the "Android can use the phone but cannot touch the boot chain" promise, enforced below the kernel. Android's own slot (a) stays writable so OTAs of Android itself still work — until they try to switch the Boot LU, which the firewall refuses; the owner switches slots from ferros.

Also M1: the kill switch at EL2. GICv3 group 0 reserved for the hv (the volume-key SPIs 29 and 32 as group 0 → FIQ → EL2 with HCR_EL2.FMO = 1), Linux keeps group 1. Linux's GICD writes to those two interrupts' group bits are trapped (GICD page) and ignored. Vol Up + Vol Down held → PSCI SYSTEM_OFF from EL2, whatever Android is doing.

### M2 — the live oracle

A ring in the hv's RAM of every trapped access (address, value, width, read/write, PC, core, timestamp) and a way to read it: ferros_pt over USB is Android's — so the oracle speaks through a shared-memory page Android exposes (a tiny root tool `cat`s it) or, better, through the display server's debug text when ferros is up next; the simplest first version is the ring surviving in the no-map region and the next ferros boot reading it (same way the report block works). Unmapping is per 4 KiB page, chosen by a list in the hv's config page: the display pipeline (DECON/DSIM/DQE/DPP) for the display bring-up, the camera blocks later, the modem's PCIe window — the register oracle the handoff used to be, but with Android alive and the phone usable while it logs.

**The oracle's targets, in the owner's order (2026-10-19): touch, data/cellular, camera, then sound (mic, speaker); proximity, thermal and the spectrometer after.** Each is a block (or a chain of blocks) whose pages the hv unmaps from the stage-2 identity map while Android drives it; the trap log of that session is the register-level truth the ferros driver is written from, the way the handoff oracle served the display. The display pipeline is already done that way; touch (SPI + the touch IC's firmware load), camera (CSIS, the ISP chain, the sensor over I3C) and cellular (the modem over PCIe, the cpif link) are the big three; mic and speaker (the audio DSP's shared memory and I2S), proximity and the spectrometer (sensor hub, AoC), thermal (the TMU) are smaller.

### Later

- A hypervisor-side PT endpoint of its own (trap the DWC3 USB controller? No: share it by owning a second endpoint in Android's gadget — too deep; the shared page is enough).
- ferros itself as the EL2 host with Android as a guest *and* ferros processes beside it (the VHE kernel and the hv merge: same stage-2 code, ferros's scheduler owns the cores). Then "boot Android" is a ferros command and the gate's Google chevron starts a guest, not a reboot.
- Signing: once both slots are signed with the owner's key and the bootloader locked, the hv is part of the signed slot-a image and Android cannot be booted without it.

## Where root was needed, and where it goes

The owner's direction (2026-10-17): a factory-signed, unrooted Android as the guest. The hv needs nothing from Android. Magisk was for the handoff era and for flipping the Boot LU from inside Android, and the firewall closes that path anyway. What root still buys today is the way back to ferros from inside Android (`tools/husky-to-ferros.sh`; SELinux refused the sysfs write even as root, so it falls back to fastboot). That moves into the hv: the kill switch at EL2 (Vol Up + Vol Down → SYSTEM_OFF whatever Android is doing, asked for on the first day) and a second chord that switches the Boot LU and reboots into ferros. Then slot a carries the hv plus Google's own signed images, untouched.

## Status

- **2026-10-17, M0 passes.** Android boots at EL1 under the hv in 30 s ("CPU: All CPU(s) started at EL1", nine cores, the reservation visible in `/sys/firmware/devicetree/base/reserved-memory/`), and ran ten minutes under GPU and GPS load (Mahere rendering tiles) with no hard-lockup warning and no cpufreq stall, after a day of freezes between one and five minutes in. Suspend/resume through `_secondary` is exercised constantly by cpuidle (thousands of power-down resumes per core per minute); a full system suspend is still to be exercised off USB.
- **The bug was the VMID.** With EL2 present, every EL1&0 TLB entry is tagged with VTTBR_EL2.VMID even while stage 2 is off, and VTTBR_EL2 is UNKNOWN at reset — a different value per core, and again after every power-down. Linux's broadcast TLB invalidations only reach entries carrying the issuing core's VMID, so the other cores kept stale translations; the damage surfaced minutes later and fastest under mapping churn (the GPU), always as the cpufreq governor thread spinning first and then cores locking up one by one ("hardlockup by hardware" from EHLD). `configure_el2` now sets VTTBR_EL2 = 0 and VTCR_EL2 and flushes the EL1 TLB on every core.
- **Fixed on the way, each measured on the glass or in pstore:** an ISB between the HCR_EL2 and CPTR_EL2 writes (the CPTR write landed in the E2H layout and ZCR_EL2 trapped, EC G#19); ACTLR_EL2 (was G#1000) opened for the EL1 implementation-defined registers; the hv built soft-float so its trap handler cannot touch guest SIMD state; EC G#18 system-register traps logged and skipped.
- **Every SMC is forwarded from EL2 (2026-10-19), the native-SMC window removed.** The hv traps each SMC (HCR_EL2.TSC), re-issues it to EL3 with `forward_smc`, and steps the guest past it; the only rewrite is the re-entry point of the three PSCI calls that carry one (CPU_ON, CPU_SUSPEND, SYSTEM_SUSPEND), swapped to `_secondary`. For two days a second path ran instead: the trap was dropped and the SMC re-executed natively from EL1 under a hardware breakpoint (OS Lock cleared, BRP0 routed to EL2 by MDCR.TDE, IRQ/FIQ routed in only for the classes the guest had unmasked), to test whether EL3 treated EL2 callers differently. The memory-corruption root cause disproved that theory, so the window and its breakpoint/OS-lock/window-IRQ machinery are gone: ~4 KB of the scariest code removed, the hv built and booted Android at EL1 without it (it had, in fact, forwarded everything before the window was ever written). This is the shape stage 2 is built on top of.
- **The kill chord at EL2 is the power cut (2026-10-17, approved on the glass: "watch that second vol button go down and if the next frame ain't black cuz the power is gone, you did it wrong").** Vol Up + Vol Down, both down on two consecutive polls, PSCI SYSTEM_OFF, the PMIC cuts the rails. The hv samples the two always-on GPIO data bits on every trap it takes (first arming them as pulled-up inputs: ABL hands them over reading "pressed"), which is microseconds apart when the phone idles and well under a frame under a busy UI; the GIC group-0 FIQ hook in M1 makes it exact. A fastboot variant (mode stamped through EL3, cluster watchdogs fired, ~20 s) was measured working the same afternoon and dropped; a direct PMU write plus PSCI reset as an instant fastboot hung the core in EL3 (ABL reads a Linux reboot's mode off the PMIC path). Fastboot is the dev's problem, through adb.
- **The Mahere freeze (open, 2026-10-17 evening).** Mahere's Vulkan rendering freezes Android under the hv within 5–60 s of launch, reproducible by hand and over adb (`tools/husky-hv-mahere.sh`: flash, boot, launch, pan, verdict). Google Maps and a CPU burn do not. The kernel's last words are always the same: the cpufreq governor threads spin, then idle cores never come back (EHLD "hardlockup by hardware"), then the panic. Bisection so far, each a build knob in `ferros_hv/build.rs`: the hv's memory map and DTB are innocent (Linux handed EL2 after them runs fine); the native-SMC window is innocent (forwarding everything from EL2 freezes too); the GPIO chord poll, the report-page writes, ACTLR_EL2, the MTE bit, the lean resume path, the EL2 I-cache, Linux's init_el2 register parity (FGT, HCRX, MPAM, SPE, TRF, ICC_SRE 0x9, CNTHP off, SCTLR_EL1 init), and an identity stage-2 map all changed nothing. Stopping the SMC trap after boot survives, but only because every core then wakes natively into Linux at EL2, so that proves nothing about EL1. The SMC inventory under GPU load (kprobe on `__arm_smccc_smc`) is ordinary: DQE histogram reads, the PMU power-mode hint, CPU_SUSPEND. Measured 21:20: the compositor is the first to notice — `hwc-display: mLastRetireFence(30) is not released during 40 ms` then `winconfig is delayed over 5 vsync`, i.e. DECON never finishes a frame once Mahere's SurfaceView is on screen (device composition, no client/G2D path), two seconds before the system goes; and a `SMC_PROTECTION_SET` (G2D's or MFC's EL3 call that reprograms a master's S2MPU) lands within a second of the launch. A screen recording (MFC encode, same protection call) does not freeze. Working theory: the DPU's DMA stalls on its S2MPU (fault in stall mode, the S2MPU driver's IRQ is not even registered, so no message) and the stalled interconnect takes the cores and the power firmware with it; why only with the kernel at EL1 is the open question — the DPU S2MPUs are now read on every stats tick. Next: the per-second per-core stats line the hv writes into the pstore ring, to see which core falls silent first and its last SMC; and the pKVM comparison (host at EL1 with PSCI relayed works in production on this phone), whose remaining difference is pKVM's own handling of host wakes and the S2MPU hyp driver.

- **2026-10-19, the direct-I/O hang (open; the readback-free build).** With the S2MPU readback gone the owner's Android no longer freezes, but Mahere shows a black screen for a minute and never opens. Measured: the first Mahere process is a zombie whose last thread (`kete-librarian`, later `Thread-3`) sits in D state in `blk_io_schedule` under `__iomap_dio_rw` — an O_DIRECT `pread64` of 4 KiB from the vault's VSF file that never returns — so ActivityManager's relaunch logs `refused to die` every time. Nothing is in flight: `/sys/block/sda/inflight` 0, no busy or dispatch list, no tag held, no UFS error, no hung-task message (the detector is off). Reproduced over adb in 8 s with `tools/husky-hv-dio-hunt.sh` (ftrace + synthetic panning) and the trace says where the chain breaks: the thread's last read is issued on CPU 7 at 81.864025 (`block_rq_issue 8,0 R 102240880 + 8`), the thread blocks at 81.864038 (`block_start` in its sched stats), the UFS request completes 0.2 ms later on the same core in softirq from the idle task (`block_rq_complete … [0]`, then `block_bio_complete 254,53 R 82641728 + 8 [0]` — the original f2fs bio's completion, so `bio_endio` reached the end-I/O callback with no error), and the thread never runs again: no `f2fs_direct_IO_exit`, 1812 other UFS completions after it, direct reads by root of the same file at the same offset work. So the request is done at the block layer and the waiter is never woken — either the end-I/O path did not call `wake_up_process` (a software-decrypt kworker in between? the keys are hardware-wrapped keyslots, so it should not be) or the wake-up was lost on an idle core, which is where the hv touches things (CPU_SUSPEND intercepted; the core resumes through `_secondary`). The second run, with scheduler/IPI/idle events added to settle that, froze the whole phone off USB instead (12:12, ~110 s after boot, no watchdog reset in 5 min) — so the freeze class is not gone either, only rarer. The stuck thread blocks any relaunch until a reboot; stock Android's Mahere never shows this.
- **2026-10-19, the reservation that never was — the root cause of every freeze and of the hang.** The pstore from a freeze at 12:25 held the hv's last stats line with its per-core counters turned to random data (`0:944EBFEBEF409AE5/1027A95C/…`, core 4 still half intact), so something was writing into the hv's statics. It was Linux: the hv's `/reserved-memory/hv@afc000000` node wrote `reg` as four cells, address 2 + size 2, while husky's `/reserved-memory` carries `#size-cells = 1` (every sibling's `reg` is 12 bytes). Linux read the first size cell — zero — and reserved nothing: `/proc/iomem` showed `880000000-affffffff : System RAM` straight through the hv, and memblock had no hole. The node's presence in `/sys/firmware/devicetree` had been taken as proof on the 17th; only memblock proves a reservation. For two days the hv's 64 MiB — its stacks, statics, report page and pstore cursor — sat in the page allocator: Mahere's buffers and the kernel's own structures landed in it and the hv's writes landed in theirs. Hence freezes under memory pressure with no fault text (a corrupted kernel structure), the SError that was only a readback hitting a powered-down domain *because the readback was there at all*, the direct-I/O hang (the `dio`'s waiter pointer or the page the request completed into, overwritten), and the quiet overnight soak (an allocation pattern that happened to miss). The fix is one cell: `reg` of 12 bytes. After it `/proc/iomem` reads `afc000000-affffffff : reserved`, memblock splits at the boundary, and Android ran six minutes under the owner's hands plus adb panning with Mahere hammering the vault — "it seems to run for the most part pretty well now". The hunt's detector was then wrong the other way: a healthy Mahere shows D in `blk_io_schedule` on most polls at thousands of switches a second; stuck now means the same `nr_switches` on two polls. The kill chord, which had stopped working exactly when the phone was frozen, works again under the same hands ("killswitch works now too"): its arming state and poll counters were in the same trampled statics, so a frozen phone and a dead chord were one event.
- **2026-10-19, stage 2 is live (transparent identity map).** HCR_EL2.VM = 1 with the 40-bit IPA map `stage2_build()` lays down: 1024 level-1 block descriptors (two concatenated 4 KiB tables, 8 KiB aligned, in the hv's reserved region), every 1 GiB block Normal write-back inner-shareable RW with the access flag set, identity output. MMIO stays MMIO because FWB is off and stage 1's Device attribute wins the combine. Built with `FERROS_HV_STAGE2=1`, Android booted at EL1 in 33 s and panned Mahere for three minutes with no fault — and booting at all is the proof the table is correct, since a bad entry faults Linux dead at the first EL1 access after the eret, long before adb. VMID is 0, set explicitly in VTTBR now rather than left UNKNOWN. This is the foundation both M1 pieces stand on: the UFS firewall unmaps the controller's pages from this map so every access traps (stage-2 data abort, EC 0x24), and the oracle unmaps a target block's pages to log them. Default build still leaves it off (`hv_stage2` gates it) until it has soaked; the knob flips cleanly between the two.
- **2026-10-19, the register oracle works; touch captured (M2 mechanism).** The stage-2 map now refines down to 4 KiB pages: `stage2_unmap(ipa)` splits the covering 1 GiB block into 2 MiB blocks and the covering 2 MiB block into 4 KiB pages (tables from a small static pool in the hv's region), then marks the target page invalid. Behind `FERROS_HV_ORACLE=1` it unmaps the touch SPI controller's page (spi@111D0000, the ST FTS touch IC's bus). Every EL1&0 access to it now faults to EL2 (EC G#24); the handler emulates it against the real register — the hv at EL2 is outside stage 2 — from the abort syndrome (ISV=1: direction, width, Rt, sign-extend), hands the guest the value, logs a compact line, and steps past the instruction. The trap frame was widened to all of x0..x30 so any data register can be emulated (it saved only x0..x18,x30 before). Proven on hardware: Android booted, the FTS touch driver probed *through* the handler (SPI init, firmware load over SPI, `input: fts`, `gti.0` created) and registered its input device — emulation is faithful, since a wrong width or register would break the firmware load. 1406 SPI accesses captured from the probe (`docs/oracle/touch-spi-111d0000.log`), a clean s3c64xx polled-transfer map: CH_CFG G#00, MODE_CFG G#08, CS G#0C, INT_EN G#10, STATUS G#14 (polled), TX FIFO G#18, RX FIFO G#1C (byte reads), packet count G#20/24, USI_CON G#C4. ## The UFS firewall: the measurement (2026-11-01)

`FERROS_HV_UFS=1` builds unmap the host controller's standard registers (G#1320_0000, alone in their page) under stage 2; every access traps and is performed by the hv, and each command a doorbell write starts is decoded from Android's list (physical addresses: no IOMMU on the UFS DMA) and counted, nothing refused. Counters in the ramoops page at G#FD60_0E00 (`ufs_command` in main.rs); they survive a warm reset only, so a session ends with a sysrq crash, not `reboot` (Android's reboot is a cold reset on husky and DRAM is lost).

One session of the owner's normal use (~10 minutes after boot): 884,040 commands (709,640 reads, 150,363 writes), 4.4 M traps (~7,000 a second, ~1-2 µs each: about a percent of a core); **no write to either boot chain (boot_* .. pvmfw_*) or to the ferros partition**; one write to frp's last block, its unlock byte unchanged and unencrypted; 287 UNMAPs, all on LU0 (their ranges not yet decoded: UNMAP carries them in its data); one write to LU1-3 (expected: Android marking its slot in devinfo, LU3); none to the well-known LUNs, no WRITE BUFFER (firmware), no opcode outside the known set, no address outside DRAM. Android ran normally throughout.


Correction, the same day: that first build read UTRD word 7 the wrong way round (it is `prd_table_length` in entries, low 16 bits, then `prd_table_offset` in dwords, high 16; zuma's DT sets `fixed-prdt-req_list-ocs`, so not the Exynos byte-granular form), so its frp-byte reading came from the wrong place and does not count. With the fields right, a session with Android's idle maintenance (trim) run by hand: 13 UNMAPs on LU0, all 13 descriptors decoded, **none reaching a boot chain or the ferros partition**; one LU3 write, none to LU1/LU2; no frp write that session, so the unlock-byte check waits for a real one.
So the firewall's rules cost normal use nothing: refuse LU0 writes and UNMAPs that touch the boot chains or the ferros partition, LU1/LU2 (the bootloaders) entirely, Boot LU switches (attribute writes), WRITE BUFFER; on frp's last block let a write through only with its final byte unchanged and encryption off (Pixel's PRDT entries are 128 bytes, `pixel_ufs_prdt_entry`; des3 bit 31 enables inline encryption, which would let RAM say one thing and the flash get another). Still to settle: LU3 (devinfo holds the slot record Android must write; whether it also holds lock state an Android with root could change), the UNMAP ranges, and a stage-2 write protection on the ramoops page (ANDROID_ONCE, RECOVERY_ONCE and these counters live there, and an Android with root can survive its own crash into them).

## The UFS firewall refuses (2026-11-01)

`FERROS_HV_UFS` builds act on the measurement (`ufs_command`, `refuse_write`). Nothing is faked: each refusal is a rewrite of Android's command before the doorbell reaches the device, so the device itself answers with an ordinary error and Linux handles it as one.
- **Writes** (WRITE 10/16) into either slot's boot chain or the ferros partition on LU0, and any write to LU1/LU2 (the bootloader's copies). The LBA is moved past every LU's end; the device answers ILLEGAL REQUEST / LBA out of range before any data moves.
- **UNMAP ranges** reaching a protected run get their block count set to 0. The rest of the list still trims.
- **Queries:** WRITE DESCRIPTOR, WRITE ATTRIBUTE of bBootLunEn (the OTA engine's slot switch) or bConfigDescrLock, and SET/TOGGLE FLAG of fPermanentWPEn are given IDN G#FF, so the device answers "invalid IDN".
- **WRITE BUFFER** (flash firmware) gets a reserved mode (G#1F).
- **Coherency:** every line the hv reads or rewrites in Android's command memory is cleaned and invalidated first. The memory is cacheable, the controller dma-coherent, and the hv's MMU off.

**Open:**
- **The check-to-fetch window.** Android can change a command between the hv's check and the device's fetch; shadow command lists close it. ## The jump to ferros (built 2026-11-01, slot b)

Power + volume up under Android stops Android where it is and boots ferros fresh, with no reset, no bootloader and no unlocked-device warning. The owner asked for exactly this: "halt Android, clear it as needed, fresh boot into ferros". Android's RAM is not kept, and no wipe is done either (owner: skip the wipe). `FERROS_HV_CORE` builds, `mod hvcore` `jump`.

**At boot, before Linux.** The hv keeps three things in its reservation, because Linux reuses the RAM they arrive in:
- the packed ferros image (G#A_FF00_0000);
- ABL's device tree (G#A_FFC0_0000);
- the last 64 KiB of the initrd, where the bootconfig sits.

The kept tree's `/chosen` initrd range is pointed at a copy below 4 GiB (G#8004_0000), since its cells are 32-bit. Android then runs under the identity stage 2.

**On the chord (the hv core):**
1. Stage 2 is invalidated (all level-1 entries, the table cleaned, `tlbi alle1is`) and SGI 0 is sent to every other core. Each Linux core faults on its next instruction, or wakes from idle into `hv_secondary`, and calls PSCI CPU_OFF from the hv. Measured: all eight off in 1-3 ms.
2. DECON's trigger is masked and the hv waits 1/16 s, so no frame is in flight.
3. Every SPI and every core's SGI/PPI is made neither active nor pending. An interrupt Linux had acknowledged would otherwise never reach ferros.
4. The caches are cleaned by set/way.
5. ferros is copied to G#8008_0000 and the bootconfig below it.
6. The display SysMMUs' translation is turned off.
7. The gate mark is set (GATE_ANSWER 6).
8. Core 0 is started at ferros's entry, and the hv core switches itself off.

A core that will not stop, or a failed CPU_ON, falls back to the reset path (FERROS_ONCE).

**After a jump** (SYS_FACTS 31 = 6), init starts the shell, the screen, touch, the attest screen and USB, but not WiFi, Bluetooth, NFC, sensors or the modem (nor their keepers). The kernel leaves the AoC, GSA and Trusty alone. Every one of those met hardware Android left running and stalled the bus or the service loop:
- the modem's register read (APM watchdog);
- the AoC start;
- the WiFi driver's write into its BAR (APC watchdog, named by the register record below).

Each comes back when its driver can bring its block up from any state, not only from the bootloader's.

**Where it stands (thirty-seven jumps, 2026-11-02): it lands.** Power + volume up from a running Android gives the attest screen in about a second, with USB, touch and the display right, from Android's full or scaled resolution. The bugs found in order: drivers meeting Android's hardware (gated off after a jump: WiFi, Bluetooth, NFC, sensors, the modem; each returns once it can bring its block up from any state); the TRNG/key lock; the X3 never launched (`x3::launch` took a non-zero boot MPIDR for a reload, so the display server and touch, which pin themselves to the X3, were never scheduled); the layer scaler, the DQE stages and DECON's configuration left at Android's (the display server now runs its full modeset after a jump). Still gated after a jump: the radios and sensors.

**Android's filesystems after a jump (2026-11-03).** The jump freezes Android where it stands: no sync, no f2fs checkpoint. What its daemons fsync'd since the last checkpoint (f2fs checkpoints about once a minute) lives only in the warm node log's roll-forward chain, which Android's next mount would replay. ferros reads Android's partitions without that replay, so it saw the checkpoint's state: the modem's `modem_userdata/replay_region.bin`, rewritten by cbd, read 0 bytes, and the modem could not start after every reboot that followed a jump. ferros_f2fs now rolls forward read-only (fs/f2fs/recovery.c's rule: the chain's nodes carrying the checkpoint's version, each fsync'd inode's up to its last fsync mark, over the NAT), writing nothing; `diag "part f2fs <part> <path>"` shows the chain and where an inode came from. Measured: modem_userdata had a chain of four nodes, the replay region's inode came from it at its full 524288 bytes, and the modem registered on NR with the data call up in 16 s.

**Tools added:**
- The kernel records each core's last register access a process asks for (SYS_MMIO_READ/WRITE: the physical address, bit 63 = write) in the ramoops page at +G#180. Boot rotates it to +G#1C8 (`bridge read FD6001C8 48`), beside the per-core notes (`PREV_NOTE_*`: the lock's holder, each core's syscall crumb, 0x90 + n inside syscall n, 0x70 + n with the thread). Together they name the stalled register.
- Slot b's hv also leaves a stage trail at G#FD60_0FD0 that survives a watchdog reset.

**Slot b, learned the hard way (2026-11-01):** flash it with `FERROS_HV_CORE=1 FERROS_SLOT_B_ONLY=1 tools/husky-cold.sh`.
- The tool signs the gate with the owner's key, writes the matching `vbmeta_b`, sets b active and checks the slot the bootloader really booted.
- Hand-flashed unsigned images and `fastboot --set-active` from a fastboot entered warm through ferros left slot b refused: the early loader reported "other slot boot ok, mark other slot as active and reboot", and three retries were gone in about 25 s.

## The way back to Android without a reboot (proposal, 2026-11-03, nothing built)

The owner asked for the circle back: from ferros to the Android that was frozen, with no reboot. Today it cannot exist, for two reasons, and each has a decision in it.

**0. ferros boots over Android's memory.** After a jump ferros lays itself out as on a cold boot: the kernel at G#8008_0000 (over Android's own image at G#8020_0000), the process pool G#8300_0000, the big pool G#A000_0000-G#B600_0000, the DMA pools, the display's framebuffers, heap, phases, sprites, canvas and the four app surfaces up to G#D200_0000. That is about 1.3 GiB of the low bank, all of it Android's. For Android to survive, ferros must live only in memory Android never had: a carve-out the hv adds to `/reserved-memory` (no-map) beside its own 64 MiB, and a ferros memory map built from that carve-out after a jump instead of the cold one. **The decision:** how much of the 12 GiB Android gives up for good. ferros's present footprint says about 1.5 GiB; the high bank is the natural place (the low bank holds the bootloader's staging and the secure carveouts), but the high bank read as decayed cells after resets (2026-10-17), so it needs its refresh measured under ferros first.

**1. ferros drives the hardware Android believes it holds.** Display, UFS, USB, WiFi, the modem, the AoC: ferros brings each up its own way, and Android's drivers would come back to registers they did not leave. The clean way through is a real suspend. The jump becomes Android's own suspend to RAM: the chord asks Android to suspend (as the power key does), every Android driver runs its suspend callback and its power domain goes off, and where Android's last core makes PSCI SYSTEM_SUSPEND (which the hv already catches: the suspend trail) the hv starts ferros instead of passing the call to EL3. The way back is the resume: ferros powers its blocks down, hands the cores back, and the hv returns from SYSTEM_SUSPEND into Android's resume entry (the address in the call's x1), where every driver's resume brings its block up from off, the path deep sleep already exercises every night. What breaks that: hardware Android keeps alive across suspend. The modem's CP keeps running and its link up (cpif), WiFi's firmware keeps running for wake-on-LAN, the AoC keeps the sensors. In this mode ferros leaves those alone: no ferros modem, no ferros WiFi, no ferros sensors while Android is resumable, or the hv tells Android to shut them in their deepest mode first. **The decision:** which devices are ferros's in a resumable jump (the display, touch, USB and the vault's UFS are the minimum), and whether a jump that wants the radios is a one-way jump, as today.

**Proposed order, once decided:** the carve-out and a ferros memory map from it (measurable alone: a jump where ferros runs only inside the carve-out, Android's memory hashed by the hv before and after); then the jump moved to Android's SYSTEM_SUSPEND; then the resume. Each step lands before the next is written.

## The boot gate (2026-10-20, built, not yet run on hardware)

The slot-a boot image is pre-assembled: `[hv][Linux Image][ferros]` (`tools/husky-hv.sh`; `--no-ferros` for the old Android-only blob). ABL boots slot a as always, which prepares Android completely, including the secure world's boot state that only the bootloader can set. Before Linux runs, the hv shows the gate (`ferros_hv/src/gate.rs`):

- It adopts ABL's splash layer (DPU on, DECON v7.6, full-screen unscaled window, translation off), saves its pixels inside the hv reservation (G#A_FD00_0000), and paints black, "Ready?", the green triangle at power and the Google chevron at volume down: the same picture as ferros's `ready.rs`.
- **Power**, or one second on dev builds: ferros. The packed image (at Linux's entry + image_size rounded up to 2 MiB, behind a 4 KiB header `FERROSGT` + length; G#8260_0000 today) is copied to G#8008_0000 and entered at EL2 with ABL's DTB in x0. A marker in the hv report page (G#A_FFFF_FF10 = "GATEFORR") tells ferros the gate is answered; ferros reads and clears it and skips its own gate.
- **Volume down**: Android. The splash pixels, the layer format and the windows go back exactly as ABL left them, one frame is pushed, the trigger is restored, and the hv carries on to Linux as before.
- **Volume up**: hold (cancels the one-second auto-choice). Both volume keys: the kill chord (power off). The watchdogs are fed while the gate waits.

## The watchdog under Android (measured 2026-10-28)

Read from Android's dmesg and /proc on husky, booted through the gate:
- **0.73 s:** the cluster watchdog ABL armed before the hand-off is *stopped* by Android's `s3c2410_wdt` driver at probe ("Watchdog cluster 0 stop done … inactive, reset disabled, irq disabled"; the same for cluster 1).
- **0.73 to 5.42 s:** no watchdog runs at all.
- **5.42 s:** init starts `gs_watchdogd` (`/system_ext/bin/gs_watchdogd`, `init.gs_watchdogd.rc`). It opens `/dev/watchdog`, which restarts cluster 0 (`WTCON 11573d`) and cluster 1's multistage watchdog, and keeps them fed from userspace from then on.
- **Also loaded:** `hardlockup-watchdog` (4 s sampling, three chances, panic = 1), a kernel-side check for a core stuck with interrupts off.

**What follows:**
- **Early hangs never reset.** An Android that hangs between the driver's probe and `gs_watchdogd` hangs forever, as it did on 2026-10-28 when first-stage init could not load its modules from slot b: init never got far enough to start the daemon. The A/B fallback cannot help either, because nothing resets and the retry count never moves.
- **Later freezes reset only if the daemon stops.** After 5.4 s a freeze resets only if it stops `gs_watchdogd` as well. The 2026-10-19 freeze that sat 5 minutes without a reset is consistent with a freeze that left that daemon (or its core) running.

**Design, for the UFS firewall milestone:** the hv owns the cluster watchdogs.
- **It traps their two register pages** in stage 2 (G#1006_0000, G#1007_0000).
- **It refuses Linux's stop:** the watchdog keeps running from ABL's arm, through Android's boot, with a generous timeout.
- **It passes Linux's restarts and keepalives through** once `gs_watchdogd` runs, so a running Android feeds it as it does today.
- **The result:** an Android that hangs anywhere, early or late, is reset, and an Android that never comes up counts down its slot's retries like a dead ferros does.
