# ferros as a Rust `std` target

Started 2026-10-27. Owner: "You don't need the filesystem layer, you can strip that out. Photon speaks native vault, and yes, there was a reason I had you bring up all the cores." The goal is the real Photon app (fluor UI, tokio, the fgtw chain) running on the device as a ferros process, not a no_std re-implementation beside it.

## Shape

- **Target:** `targets/aarch64-unknown-ferros.json` — `target_os = "ferros"`, static PIE (the kernel loads a process anywhere in its arc, `ferros_sys::relocate` fixes the RELA table), `has-thread-local` (TPIDR_EL0 is the thread pointer), panic = abort, x24–x28 reserved (x28 is the arc base the kernel hands every thread).
- **Kernel:** the trap `Frame` carries TPIDR_EL0 (`tpidr` at `[sp, #816]`, 832-byte frame) since 2026-10-27, so each thread of a process keeps its own thread pointer across entries and slices. Nothing else in the kernel changes for std: threads are `SYS_THREAD_SPAWN`, blocking is `WAIT`/`WAKE` on an address (the futex), time is `cntvct_el0`, memory is the arc.
- **Runtime crate `ferros_rt`** (this repo, no_std, `rustc-dep-of-std` feature as the motor port's `moto_rt`): syscalls, futex, thread spawn with a TLS block per thread and a join futex, the allocator (TLSF behind a futex lock since 2026-11-11; ported from `ferros_heap`'s free list before), console stdio (grant slot 0), entropy (`fill_bytes`), exit, and the crt0 `_entry` that relocates, sets TPIDR_EL0 for the main thread and calls C `main`.
- **std fork:** `/mnt/Harbor/Code/ferros/forks/rust/library` — rustc 1.97.0-nightly (d7f14d3d8 2026-05-15) rust-src, with `sys/pal/ferros` and a `target_os = "ferros"` arm in each `sys/<area>/mod.rs` dispatch (pal, thread, sync futex, thread_local native, time, alloc, random, stdio, exit). Everything a process has no business with on ferros — fs, net sockets, process, env, args, pipes, fds — is `unsupported`: Photon speaks the vault natively and its sockets are the `ip` server's endpoints behind a ferros `mio` backend.
- **Build:** `cargo +nightly build -Zbuild-std=core,alloc,std,panic_abort --target targets/aarch64-unknown-ferros.json` with `__CARGO_TESTS_ONLY_SRC_ROOT=/mnt/Harbor/Code/ferros/forks/rust/library`.

## Build and run

```bash
tools/std-build.sh std/hello            # std from the fork, the ferros target, objcopy → stdhello.bin (65 KB)
cargo run -p ferros-bridge -- spawn std/hello/target/aarch64-unknown-ferros/release/stdhello.bin --name stdhello --entropy
```

The first std program ran 2026-10-27: `println!`, a `.tdata` thread-local read back exactly in main and in four spawned threads, joins, `Mutex` + `Condvar`, eight detached threads, `HashMap`, a 100 ms sleep that took 100 ms, `SystemTime` from the PMIC clock, exit 0 — 150 ms end to end.

## How the pieces fit

- **The image header** (`crates/rt/src/start.rs`, `crates/rt/ferros.ld`): offset 0 is `b __ferros_start`; offset 8 is `ferrosRT` and five absolute words the linker script computed — the zeroed tail (`.bss` + 16 + the heap), the TLS image size, the TLS block size, the TLS alignment, the heap size. The kernel reads the tail before the process runs (`process.rs image_tail`) and grows the arc by it, with the spawn input moved past it; the runtime reads the rest after. A flat image cannot carry `.bss`, and the input used to land right behind the code — this is how a std image gets its zero memory without sending it over USB. `--defsym __ferros_heap=<bytes>` sets the heap (2 MiB default).
- **The heap** is the tail after `.bss` up to the input, plus the arc's slack past the input up to the guard page under the kernel's 64 KiB entry stack, plus what the arc grows by (ARCS.md step 2). The main thread runs on a 1 MiB stack from the heap (`MAIN_STACK`); thread stacks and TLS blocks come from it too. See "The heap" below.
- **TLS** is native (`has-thread-local`, local-exec after lld's relaxation): per thread a block in TPIDR_EL0 laid out as lld computes TPOFF for AArch64 — 16 bytes of TCB, then the image at `16 + ((p_vaddr − 16) & (p_align − 1))`, `.tdata` copied in, `.tbss` zero. The kernel saves and restores TPIDR_EL0 in the trap frame.
- **Threads** end in assembly with no stack access after the state word settles (1 joinable-exited, 3 detached-exited), so the joiner or the next spawn's reaper can free the stack without racing a thread still on it.
- **Thread stacks** (2026-11-14, Photon on the Pro: `Photon.9: FAULT esr G#8A000000`, a PC alignment fault on a return address and x29 nobody wrote, ~400 ms after its alias thread finished): stacks come from the heap, and until then they were 256 KiB with nothing under them. Photon's alias thread signs its device list through fgtw's `SigningBundle::eggs` (242 KiB of frame) and fn-dsa's key decode under it (116 KiB), about 370 KiB in all, so it ran ~110 KiB past its stack's end over whatever the heap kept below; inline stack probes only write zeros there when no guard page catches them. Now every stack (each thread's and the main thread's) is page-aligned with a guard page under it that the kernel holds kernel-only (ARCS.md, `ARC_GUARD`): a run past the end faults there, the console says so and names the thread. The thread hands its guard back in its last act, before its state settles. A thread that names no size gets `ferros_rt::thread::DEFAULT_STACK`, 1 MiB (owner, 2026-11-14: "1MB"; a stack is fully committed on ferros, so half of Linux's 2 MiB, with the guard page making any overflow loud); the main thread keeps 1 MiB (`MAIN_STACK`). Measured from the crashing build's disassembly (`objdump -d`, the prologues' `sub sp` and probe loops): rav1d's worker task, symphonia's FFT twiddle tables and fgtw's signing each want more than 240 KiB in one frame.
- **Thread names** reach the kernel (SYS_THREAD_NAME, 44, from std's `set_name`), and a FAULT line carries them: `Photon.9 (alias): FAULT …`.
- **The fork's side of both** (`library/std/src/sys/thread/ferros.rs`, applied once ferros_rt has them in the main checkout, which the fork builds against): `DEFAULT_MIN_STACK_SIZE = ferros_rt::thread::DEFAULT_STACK`, and `set_name(name)` calls `ferros_rt::thread::set_name(name.to_bytes())`.
- **A panic** (2026-11-18, KERNEL.md "A process that dies"): std's default hook hands the kernel the message, the file, the line and the column (`ferros_rt::panic_report`, SYS_PANIC 46) before it prints, and the abort that follows ends the process with them; the kernel adds the thread's name and the frame-pointer chain, and the flash log keeps the death as typed fields (`ferros-bridge deaths`). The target keeps a frame record in every function (`"frame-pointer": "always"`), std's own included (build-std). A custom hook (`set_hook`) replaces the default and tells the kernel nothing.
- **The fork's side of the panic** (`library/std/src/panicking.rs`, `default_hook`, right after `let msg = payload_as_str(info.payload());`; applied once ferros_rt has `panic_report` in the main checkout, which the fork builds against; until then a copy of the fork with its `ferros-rt` path at the worktree's, as the 2026-11-18 run used): `#[cfg(target_os = "ferros")] ferros_rt::panic_report(msg, location.file(), location.line(), location.column());`.
- **The futex** is the kernel's WAIT/WAKE on a 64-bit word: `Futex = AtomicU64` for both widths.
- **memcpy, memmove, memset** (2026-11-17, `crates/rt/src/mem.rs`): ferros_rt's own, by q-register pairs, strong symbols over compiler-builtins' weak word loops (the `compiler-builtins-mem` feature still provides `memcmp`, `bcmp` and `strlen`). Up to 64 bytes the first and last 2^k bytes (overlapping, no byte loop); past 64 the last 64 loaded first, the 64-byte blocks, the last 64 stored; `memmove` runs the blocks from the end when the destination is above the source within the length. The loops are inline assembly, since a copy loop in Rust is what LLVM turns back into a call to `memcpy`. Checked on the Pro by `std/memcheck` against a volatile byte-at-a-time reference: every length to 2^9 plus 2^12 + 1 and 2^16 + 3, sixteen source alignments, five destination offsets, every `memmove` overlap within 2^7 either way, guard bytes either side: 2,159,248 cases, none wrong. Measured by `std/membench` (2^24-byte buffers, one thread): `memcpy` 13.0 to 20.8 GB/s and `memset` 8.4 to 25.4 GB/s at the active tier (A715s 1065 MHz, MIF 2028, DSU 1197), 24.3 to 30.6 and 18.1 to 33.3 at the lift's clocks (2367, 3744, 1800); four threads unchanged (the memory's limit, 32 and 40 GB/s). A std app gets them at its next build with ferros_rt's fingerprints cleared (memory std_rebuild_ferros_rt); no_std payloads (ferros_sys) still use compiler-builtins'.
- **Entropy**: the entry probes the grants for an Entropy capability (`--entropy`); without one `std::random` falls back to a counter-seeded mixer, fine for `HashMap`, not for keys.

## The heap

Every std process (Photon, Mahere, Genesis) allocates thru `ferros_rt::alloc`, so this is everyone's malloc.

- **Until 2026-11-11** it was `ferros_heap`'s first-fit free list behind one spinlock: every alloc walked the list twice, every free once, and Mahere's loader, label and vault threads left 20-50 thousand free blocks on it. Its drawing thread makes about 570 heap calls a frame and waited behind the others' walks: about 65 % of the process's CPU was in the heap, mostly spinning, and a holder preempted mid-walk left every other thread spinning out its 10 ms slice.
- **Now: TLSF** (`crates/rt/src/tlsf.rs`, two-level segregated fit): 28 × 32 free lists by size class, two bitmaps, so an alloc or a free is a few bit operations and list links whatever the number of free blocks. Good fit (the least class that fits), so the big block at the top is split only when nothing smaller serves. A 16-byte header a block (the block before, the size and the free bit), payloads 16-aligned, 32 bytes the least block; a free merges with both neighbours at once; each region ends in a size-0 sentinel. `realloc` works in place first: a shrink cuts the tail off, a grow takes the free block behind (a Vec doubling over free space moves nothing).
- **The lock** (`crates/rt/src/lock.rs`): a futex mutex over the kernel's WAIT/WAKE, the shape of std's own Mutex here: 128 loads of spinning, then the waiter sleeps until the holder's unlock wakes it. Nothing spins without end; a preempted holder costs the waiters only the wait. The thread registry uses it too. No kernel change was needed.
- **The arc**: grows as before (ARCS.md step 2), each grow joined to the last one's region; and gives back from the top (`ARC_SHRINK`) when the free block at the top of what it grew passes a cushion (ARCS.md, "ferros_rt gives back"). Never `ARC_RELEASE`: a hole in the middle of a native arc is never refilled.
- **No per-thread caches**: on Mahere's harness the heap now costs what the host's malloc costs (below), so they would add hoarding and a flush at every thread's end for nothing measured.
- **Tests and numbers** (`tools/rt-heap`, x86_64 Linux: `cargo test --release`, `taskset -c 0-3 cargo run --release --example bench`): the runtime's own tlsf.rs, lock.rs, layout.rs and alloc.rs by path, over Linux's futex and a fake arc whose given-back frames are unreadable. A shadow map checks that no byte is handed out twice (166 thousand blocks of 1 B-32 MiB at alignments to 64 KiB, the heap's lists and regions walked every 4096 operations); eight Mahere-shaped threads make 707 thousand calls over a growing and shrinking arc (9 grows, 4 shrinks, 174 MiB at the peak, 36 MiB at the end). One thread, a ring of 16 B-4 KiB blocks: the free list took 130 ns a call fresh, 135 µs at 20 000 free blocks and 187 µs at 50 000; TLSF 20-22 ns at all three, glibc 18-22 ns. Eight threads on four cores for 4 s: the free list's drawing thread made 8 frames (528 ms a frame in the heap), TLSF's 5720 (0.67 ms; 1.2 µs a call, all of it the lock under eight threads that do nothing else), glibc's (per-thread arenas) 56 thousand.
- **Mahere's frame harness** (mahere-device `examples/ferros_frames.rs`, 60 s at 1344 × 2992 under `taskset -c 0-3`, cells from the bucket each held back 10 s): the free list, frames of 0.4-0.9 s with 120-460 ms of each in the heap, 279 % CPU, 29 cells in by 55 s; TLSF, 0.1 ms a frame in the heap, 90 % CPU, 70 cells in; the host's malloc, 89 % CPU, 70 cells.
- **After a change to the heap**, every std app is rebuilt (Traps below: delete ferros-rt's fingerprint first).

## Traps met

- Under `relocation-model = pic` rustc reaches an extern static through a GOT entry — and the GOT entries are exactly what `relocate()` has yet to fix. `relocate()` finds its three linker symbols with PC-relative `adrp` in asm (`sys::pc_rel!`); the first hello faulted in the heap setup on an unrelocated `__bss_end`.
- cargo's build-std does not notice edits to a path dependency of std: after changing `ferros_rt`, clear `target/aarch64-unknown-ferros/release/{.fingerprint,deps}` of `ferros-rt-*` and `std-*` (or `rm -rf target`).
- `panic_immediate_abort` is a panic strategy now, not a std feature; `compiler-builtins-mem` must be in `build-std-features` or `memset` is undefined at link.
- The handle-guard pre-commit hook takes the better part of an hour over the 58 MB first commit of the std fork.

## The substrate, piece by piece (all 2026-10-27)

- **tokio** multi-thread runtime (`rt`, `rt-multi-thread`, `sync`, `time`, `macros`; no `net`, which needs mio and socket2 and a libc): `std/probe` ran 8 tasks over 4 workers with timers in 71 ms. Photon's sockets will be a ferros socket type over the `ip` server, not tokio's.
- **kete** over the kernel vault (`kete/src/ferros.rs`): the process's Store scope, every entry by the 32-byte address kete already derives, passed to the kernel as those bytes (SYS_STORE bit 5), values in 4 KiB pieces (staged writes, delete, list). The probe wrote a 10 KB value, read it back exact, listed, deleted. No `dirs`, no files.
- **getrandom** 0.2/0.3/0.4 custom backends in `ferros_rt` (`--cfg getrandom_backend="custom"` and the 0.2 `custom` feature from the program's side) — the kernel's entropy or an error, never the mixer.
- **fluor** `host-ferros` (`fluor/src/host/ferros/mod.rs`): the Android shell's twin over the display server's app surface (op 22, 16-bit gamma-2 working values from fluor's gamma-2.2 darkness bytes through one table) and the touch server's contact records (the first finger is the pointer; pinch waits for the input work). `std/fluordemo` draws text and counts taps in a 448 × 996 frame; spawn it with `--use display --use touch --dma app-surface --entropy`.
- **Memory**: `cachemap::POOL_BIG`, 512 MiB at G#A000_0000 in 2 MiB blocks (nothing in the device tree reserves G#9800_0000-G#C000_0000), a second buddy pool for arcs of 16 MiB and up (and small ones when the page pool is full); masked arcs stay in the page pool for their per-page W^X. The demo's 64 MiB arc (3.3 MB image + a 32 MiB heap by `--defsym __ferros_heap=`) is the first from it.
- **C in the graph**: `tools/std-build.sh` points the cc crate at `aarch64-linux-gnu-gcc` freestanding with `tools/std-sysroot/include` (string, stdlib, assert, stdio, inttypes, math, unistd, features: declarations only, the mem routines are compiler_builtins'), and the PQClean KEM suites build and run — ML-KEM-768 round-trips on the device in 572 µs. Crates that spell C types through `libc` (pqcrypto-internals, rav1d) take the fork at `/mnt/Harbor/Code/ferros/forks/libc` (libc 0.2.183 plus a `ferros` arm of scalar types, no functions): `[patch.crates-io] libc = { path = … }` and `cargo update -p libc`. fluor's `icon` feature stays off on ferros until rav1d is tried through that fork.

The gate verifies the Ed25519 signature in place (`oracle::gate_located`: the 64 signature bytes zeroed inside the arc, hashed, verified, put back): vsf's verifier copies the whole file first, and that copy killed the kernel on the first try. `FERROS_STREAM=1` forces the path for small images.
- **Photon Transport moved 215 KB/s** (477-byte packets, one at a time) until 2026-10-31: the bridge slept 1 ms after every packet. ## Receives on a doorbell (2026-11-13)

- **Where the calls came from** (the 8a, `diag sched`, screen on, at rest): Photon called ip 949 times a second and fgtw 166. Neither was std's: std's sockets are `unsupported` here, and ferros_rt has none. Photon's own `platform/ferros_net.rs` asked RECV every 2 ms a socket (the async socket over a tokio sleep, the blocking one over a thread sleep); fgtw's loop asked RECV on 4383 and 4384 and INFO every 20 ms. The socket layer of a std app on ferros is the app's (Photon's ferros_net, Mahere's net over ip), so each carries the fix.
- **Found on the way:** fgtw and Photon both read 4383 and 4384 from ip's one queue, so each datagram went to whichever asked first (Photon, polling ten times as often, took most of fgtw's fleet frames).
- **ip** (payloads/ip): op 11 WATCH, one held call over a set of ports and INFO's flags, answered when a watched port holds a datagram newer than the one its caller was told of, when the flags change (a route, the call, the person), at its deadline or at op 12 KICK; nothing taken from the queue, the number passed back, so a datagram not yet read never answers again. Op 13 UNWATCH retires a reader. Each watch's (id, port) is a reader: a datagram of a watched port waits until each reader has taken it, and RECV names its reader. Op 2 holds to an exact counter deadline (a read timeout).
- **fgtw**: a watcher thread holds one WATCH and rings a word; the loop reads a port only when named and waits with `wait_world_or_call` on the word, its endpoints' calls and its next real deadline (the beacon's 3 s, the space's 4 s join, the look-ups); 1 ms while PT or work is in hand and 20 ms while the person is at the Fleet page, as before.
- **Photon** (photon branch ferros-net-held): one watcher thread a process wakes the tasks of the ports named; a blocking receive is held at ip to its timeout.
- **Measured after** (the 8a, 2026-11-13, a reboot, attest, Photon launched; three LAN hosts sending Photon frames to 4383, about 3 a second): screen on, Photon 5.8 + 1.2 (its watcher) calls a second and fgtw 4.6 + 1.2 (`diag sched`); dark, Photon 4.6 + 1.0 and fgtw 10.8 + 1.0; ip's 64 s line in the dark, A#924 app requests for A#185 datagrams each taken by both readers (about 2.5 calls a datagram a reader: the watch's answer, the RECV that takes it, the RECV that finds the port empty), so with nothing arriving the calls are the deadlines' alone. A datagram's wait in ip's queue until its reader took it: screen on, Photon 0.34 ms on average (3.5 ms longest), fgtw 2.2 ms (148 ms longest, its loop busy signing at launch); dark, 1.5 to 1.9 ms on average, 49 ms longest. fgtw reached fgtw.org (the space's copy, the fleet key) after the reboot.

## TCP (2026-11-18)

One TCP client for every std app, in `ferros_rt::tcp` (branch rt-tcp), over the ip server's client TCP. Until now each app carried its own over ip's ops 4-7: fgtw's `post` (no_std), Photon's `platform/ferros_http.rs`, Mahere's `net`. Photon's fgtw.org calls (signed VSF over plain HTTP/1.1 on port 80, Claude memories/fgtw_plain_http_for_ferros.md) and its relay WebSocket are what it is for.

- **Taking it:** std keeps its own copy of ferros_rt to itself (an app cannot name a crate of the sysroot), so an app takes a second copy as a library: `ferros-rt = { path = "<ferros>/ferros_rt", default-features = false }` (under `[target.'cfg(target_os = "ferros")'.dependencies]` in a crate that also builds elsewhere). Feature `runtime` (default, and std's copy) carries the image's entry and every symbol the link takes by name (the C allocator, memcpy and kin, getrandom's backends); the app's copy leaves it off, so the two never collide at the link. The copy's `grants()` is 0, which is where the kernel puts the grants page, so its `cap` is right.
- **The API:**
  - `Ip::at(slot)`: the ip server thru the process's grant of the `udp` endpoint (`--use udp`) at that slot, the spawn line's order. The grants page names no endpoint, and probing each grant would send an ip request to whatever server holds it, so the app says where its `udp` is.
  - `Ip::resolve(host, Family::{Any, V4, V6}, until) -> Result<IpAddr, Error>`: op 10, held until the lookup ends (four tries a second apart).
  - `Conn::connect(ip, SocketAddr, until) -> Result<Conn, Error>`: v4 or v6 (a v4-mapped v6 goes as v4); returns when ip says the connection opened, or failed (`Refused` for a reset while connecting, `Unanswered` when the SYN was), or at `until` (`TimedOut`).
  - `Conn::read(&self, buf, until) -> Result<usize, Error>`: held at ip until data lands or the state changes; `Ok(0)` is the peer's close once everything before it was read. Up to 256 KiB a call, landing in `buf` itself (the state byte first, the data moved down one).
  - `Conn::write(&self, buf, until) -> Result<usize, Error>` (4094 bytes a call at most, what ip's send buffer takes) and `write_all`: a send that finds the buffer full is held at ip until the room it asked for is free.
  - `Conn::close(self)`, and `Drop` closes the same (op 7: a FIN after the data taken, freed once both sides closed or 16 s on).
  - `Until::after(Duration)`, `Until::at(ticks)`, `Until::NEVER`: the caller's deadline on the counter, handed to ip with each held call, which answers at exactly then. A protocol's real deadline (an HTTP exchange's 16 s, as fgtw's post has) or none.
  - `Error`: NoServer, NoRoute, Busy, NoMemory, Refused, Reset, Unanswered, TimedOut, Gone, NoAddress, BadName, NoAnswer, BadReply.
- **Send and Sync, not split halves:** read and write take `&self`, so one thread reads while another writes, std's `TcpStream` shape (`Read`/`Write` for `&TcpStream`, an `Arc` for `try_clone`). The two directions are two places at ip (a connection's held receive and its held wait for room), so neither waits on the other. Two readers on one `Conn` take turns on its read lock (two writers on its write lock): ip keeps one held receive a connection, and a second would answer the first early, each pushing the other out. Halves would say the same in types, but every std mapping would have to join them again.
- **No polling anywhere:** a connect is a receive that takes nothing, held until the state leaves "connecting"; a read is held until data or a state change; a full send buffer is waited out on op 14; while nobody is present (ip answers every request with nothing then) the client holds a WATCH naming no ports until the person bit of ip's flags is back. Each wait is one held call; the host tests count them.
- **ip's side** (payloads/ip's header has the bytes):
  - op 6's deadline form: eight bytes after `most`, an exact counter deadline (u64::MAX until something changes), in place of the wait byte's 1 to 255 seconds; its state byte says why a failed connection failed in the high four bits (1 reset, 2 unanswered). The client puts 255 in the wait byte too, so an ip from before holds the call 255 s rather than answering it at once again and again.
  - op 14 TCP ROOM: [14, handle, want, deadline] → [state, room], held while the send buffer has less room than `want`.
  - Each connection has its own place for a held receive and a held wait for room (`TcpHeld`): until now a TCP receive took one of the sixteen places the UDP receives share, and a seventeenth reader pushed out the oldest, which held again and pushed out the next.
  - A freed connection answers its held calls at once (`[5]`), and a connection with a held call is never reaped as idle: after an idle sleep past 32 s (ip sleeps until its next deadline, the group reports' 60 s) the reap ran before the pass marked the held connection touched, so a quiet WebSocket's reader would have been reset.
  - Everything else answers as before; fgtw's post is unchanged.

## basecalc on the device (2026-11-17)

- **The first std app with a C library built by configure**: basecalc's numbers are rug's, over GMP 6.3, MPFR 4.2 and MPC 1.3, and the gmp-mpfr-sys crate builds those with their own configure scripts, which know no ferros. tools/basecalc-build.sh builds them first, from the crate's own sources, and hands them to the crate as its cache (`GMP_MPFR_SYS_CACHE`, laid out as its build.rs reads one: `<cache>/<major.minor>/aarch64-unknown-ferros/<version>/`), so the crate copies them in and runs no C build of its own. GMP's portable C rather than its AArch64 assembly (the assembly is not held off x24 to x28); MPFR without thread-local state (one thread runs the engine). No instruction of the linked C names x24 to x28 (objdump of the image).

The allocator is ferros_rt's, the mem routines, the libm subset and the quad-precision float routines compiler_builtins'.

## C++ through ferros_rt (2026-11-24)

The owner, 2026-11-24 ("Yes and yes"): OpenH264 (Cisco's H.264 codec, C++) on ferros through Rust shims in ferros_rt, with no C++ runtime library. H.264 is the house format for beam video (AGENT.md Rule -1); Photon encodes and decodes beams with it (photon docs/ferros-media.md).

- **The source:** OpenH264 v2.7.0, a shallow clone at /mnt/Harbor/ferros-ref/openh264 (commit 1bca62311e447fd9c39fc93de2c4b96cd5ce971c): `git clone --depth 1 --branch v2.7.0 https://github.com/cisco/openh264 /mnt/Harbor/ferros-ref/openh264`. `OPENH264_SRC` names another; the build refuses a checkout whose codec_ver.h is not 2.7.0. Photon's other platforms build 2.6.0 (crates.io's openh264-sys2 0.9.8 vendors it); the API headers are the same but for the version, so the same bindings serve, and the bitstream is H.264 either way.
- **The crate:** `std/openh264-sys2`, a fork of openh264-sys2 0.9.8 (the crate Photon already uses): its `src/` the crate's own less the `libloading` paths, plus one line that links ferros_rt's shims, its `build.rs` building OpenH264 for `aarch64-unknown-ferros` only, its C header set in `c/include`. An app takes it in place of crates.io's with `[patch.crates-io] openh264-sys2 = { path = ".../ferros/std/openh264-sys2" }` and keeps the `openh264` crate's API, so Photon's `src/wave/h264.rs` builds for ferros as it is, given `target_os = "ferros"` in its cfgs. A fork, not a new binding crate: Photon's code is unchanged and one API serves every platform.
- **How it is built:** the cross g++ (aarch64-linux-gnu-g++), through the cc crate, the four libraries (common, processing, decoder, encoder) and their arm64 assembly (NEON). Flags (each with its reason in build.rs): `-ffixed-x24` to `-ffixed-x28`, `-mbranch-protection=none`, `-ffreestanding -fbuiltin` (no host headers, but a fixed-size memcpy still inlines), `-fno-exceptions -fno-rtti -nostdinc++`, no unwind tables, `-fno-math-errno`, `-mno-outline-atomics`, `-march=armv8.2-a`, upstream's `-O3 -DNDEBUG -fno-strict-aliasing -fno-common`. No libstdc++ is linked (`cpp_link_stdlib(None)`). The assembly names none of x24 to x28 (grep of the sources), and in the linked image every use of them is a read of x28 or x27 by ferros_rt (objdump: 141 instructions, all `mov xN, x28` or `x27`); no PAC or BTI instruction.
- **The header set** (`std/openh264-sys2/c/include`): declarations only, each answered by ferros_rt or std's copy of it; a name OpenH264 does not use is not declared, so a new use fails at compile time, and a declared name nothing defines (`localtime`, `strftime`, for the uncalled `WelsStrftime`) fails at link if it is ever called.
- **ferros_rt feature `cxx`** (an app's copy only; the fork turns it on, so only a process that links C++ carries it): 
  - `cxx.rs`: `operator new` and `delete` in every form (sized, array, aligned, nothrow, `std::nothrow`), over std's copy's C allocator (an alignment past 16 over-allocates and keeps the block's start below the object); a failed throwing `new` ends the process with the allocator's out-of-memory line (nothing can catch `bad_alloc`); `__cxa_pure_virtual` and `__cxa_deleted_virtual` end it with a report; `__cxa_guard_acquire`/`release`/`abort` on the guard word with the kernel's futex (a second thread sleeps until the first finishes); `__cxa_atexit` keeps nothing (a ferros process runs no destructors at exit); `__dso_handle`.
  - `posix.rs`: `pthread_create`/`join`/`self` on ferros_rt threads (a 1 MiB stack with its guard page, as std's), the attribute calls (scope and policy kept, not acted on: the kernel has one class), mutexes on lock.rs's futex lock (now shared as `lock::acquire`/`release`: the heap lock's own algorithm, 128 loads of spin then sleep), condition variables as a futex sequence word, counting semaphores as a count and a sleepers word (a post with nobody waiting makes no syscall), timed waits to an exact counter deadline (`futex_wait_until`), `usleep` as SYS_SLEEP to a deadline, `sched_getaffinity` as std's four A715 workers, `getpid` 0, `strncpy`, the thread's `errno`. Every clock (`clock_gettime`, `gettimeofday`) is the counter since the device started: OpenH264 takes differences and makes absolute deadlines for its timed waits that the same clock reads, so no wall time and no UNIX time is given.
  - `stdio.rs`: a real formatter, since OpenH264's trace prints its warnings and errors to `stderr` (now the console) and formats a tag for every log call: flags, width, precision (`*` too), the lengths, and `d i u x X o c s p f F %`; any other conversion is written as it stands and reads no argument, `%n` never writes. `vsnprintf`, `snprintf`, `printf`, `fprintf`, `vfprintf`, `fwrite` to the console; `fopen` answers null (no files), `fclose`, `fflush` and `fseek` do nothing.
  - The app copy's heap: with `cxx`, its `alloc`, `dealloc` and kin go to Rust's global allocator, std's copy's heap, so the threads it starts take their stacks and TLS blocks from the process's one heap (alloc.rs). std's copy is unchanged.
  - Not needed after all: `getauxval` (OpenH264 detects NEON at run time only on 32-bit ARM and LoongArch) and `sysconf` (Fuchsia only); neither is defined.
- **Known waits in OpenH264 itself:** a thread pool's start waits for its thread in 1 ms sleeps (`WelsThread::Start`) and its teardown in 10 ms sleeps, and `WelsMultipleEventsWaitSingleBlocking` without a master event tries each event and sleeps 1-2 us between rounds; these are upstream's, once per encoder at start and end, not per frame (the encoder's per-frame work waits on semaphores).
- **The test:** `std/h264bench` (`tools/std-build.sh std/h264bench`, image 1.12 MB; spawn with no grants): the shims as C calls them (four pthreads counting under one mutex, a condition variable, a static-init guard raced, a semaphore round trip timed, `sem_timedwait` and `pthread_cond_timedwait` to a 2 ms deadline), the `openh264` crate's Encoder and Decoder with Photon's settings, then the raw API with fixed slice counts and encoder threads: 32 synthetic frames a case (a scrolling gradient, a textured square crossing, noise), baseline, 4 Mbit/s at 30 frames/s, each decoded and its luma PSNR checked against 30 dB.
