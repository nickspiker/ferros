# ferros as a Rust `std` target

Started 2026-10-27. Owner: "You don't need the filesystem layer, you can strip that out. Photon speaks native vault, and yes, there was a reason I had you bring up all the cores." The goal is the real Photon app (fluor UI, tokio, the fgtw chain) running on the device as a ferros process, not a no_std re-implementation beside it.

## Shape

- **Target:** `targets/aarch64-unknown-ferros.json` — `target_os = "ferros"`, static PIE (the kernel loads a process anywhere in its arc, `ferros_sys::relocate` fixes the RELA table), `has-thread-local` (TPIDR_EL0 is the thread pointer), panic = abort, x24–x28 reserved (x28 is the arc base the kernel hands every thread).
- **Kernel:** the trap `Frame` carries TPIDR_EL0 (`tpidr` at `[sp, #816]`, 832-byte frame) since 2026-10-27, so each thread of a process keeps its own thread pointer across entries and slices. Nothing else in the kernel changes for std: threads are `SYS_THREAD_SPAWN`, blocking is `WAIT`/`WAKE` on an address (the futex), time is `cntvct_el0`, memory is the arc.
- **Runtime crate `ferros_rt`** (this repo, no_std, `rustc-dep-of-std` feature as the motor port's `moto_rt`): syscalls, futex, thread spawn with a TLS block per thread and a join futex, the allocator (TLSF behind a futex lock since 2026-11-11; ported from `ferros_heap`'s free list before), console stdio (grant slot 0), entropy (`fill_bytes`), exit, and the crt0 `_entry` that relocates, sets TPIDR_EL0 for the main thread and calls C `main`.
- **std fork:** `/mnt/Harbor/Code/ferros-rust/library` — rustc 1.97.0-nightly (d7f14d3d8 2026-05-15) rust-src, with `sys/pal/ferros` and a `target_os = "ferros"` arm in each `sys/<area>/mod.rs` dispatch (pal, thread, sync futex, thread_local native, time, alloc, random, stdio, exit). Everything a process has no business with on ferros — fs, net sockets, process, env, args, pipes, fds — is `unsupported`: Photon speaks the vault natively and its sockets are the `ip` server's endpoints behind a ferros `mio` backend.
- **Build:** `cargo +nightly build -Zbuild-std=core,alloc,std,panic_abort --target targets/aarch64-unknown-ferros.json` with `__CARGO_TESTS_ONLY_SRC_ROOT=/mnt/Harbor/Code/ferros-rust/library`.

## Build and run

```bash
tools/std-build.sh std/hello            # std from the fork, the ferros target, objcopy → stdhello.bin (65 KB)
cargo run -p ferros-bridge -- spawn std/hello/target/aarch64-unknown-ferros/release/stdhello.bin --name stdhello --entropy
```

The first std program ran 2026-10-27: `println!`, a `.tdata` thread-local read back exactly in main and in four spawned threads, joins, `Mutex` + `Condvar`, eight detached threads, `HashMap`, a 100 ms sleep that took 100 ms, `SystemTime` from the PMIC clock, exit 0 — 150 ms end to end.

## How the pieces fit

- **The image header** (`ferros_rt/src/start.rs`, `ferros_rt/ferros.ld`): offset 0 is `b __ferros_start`; offset 8 is `ferrosRT` and five absolute words the linker script computed — the zeroed tail (`.bss` + 16 + the heap), the TLS image size, the TLS block size, the TLS alignment, the heap size. The kernel reads the tail before the process runs (`process.rs image_tail`) and grows the arc by it, with the spawn input moved past it; the runtime reads the rest after. A flat image cannot carry `.bss`, and the input used to land right behind the code — this is how a std image gets its zero memory without sending it over USB. `--defsym __ferros_heap=<bytes>` sets the heap (2 MiB default).
- **The heap** is the tail after `.bss` up to the input, plus the arc's slack past the input up to the guard page under the kernel's 64 KiB entry stack, plus what the arc grows by (ARCS.md step 2). The main thread runs on a 1 MiB stack from the heap (`MAIN_STACK`); thread stacks and TLS blocks come from it too. See "The heap" below.
- **TLS** is native (`has-thread-local`, local-exec after lld's relaxation): per thread a block in TPIDR_EL0 laid out as lld computes TPOFF for AArch64 — 16 bytes of TCB, then the image at `16 + ((p_vaddr − 16) & (p_align − 1))`, `.tdata` copied in, `.tbss` zero. The kernel saves and restores TPIDR_EL0 in the trap frame.
- **Threads** end in assembly with no stack access after the state word settles (1 joinable-exited, 3 detached-exited), so the joiner or the next spawn's reaper can free the stack without racing a thread still on it.
- **The futex** is the kernel's WAIT/WAKE on a 64-bit word: `Futex = AtomicU64` for both widths.
- **Entropy**: the entry probes the grants for an Entropy capability (`--entropy`); without one `std::random` falls back to a counter-seeded mixer, fine for `HashMap`, not for keys.

## The heap

Every std process (Photon, Mahere, Genesis) allocates thru `ferros_rt::alloc`, so this is everyone's malloc.

- **Until 2026-11-11** it was `ferros_heap`'s first-fit free list behind one spinlock: every alloc walked the list twice, every free once, and Mahere's loader, label and vault threads left 20-50 thousand free blocks on it. Its drawing thread makes about 570 heap calls a frame and waited behind the others' walks: about 65 % of the process's CPU was in the heap, mostly spinning, and a holder preempted mid-walk left every other thread spinning out its 10 ms slice.
- **Now: TLSF** (`ferros_rt/src/tlsf.rs`, two-level segregated fit): 28 × 32 free lists by size class, two bitmaps, so an alloc or a free is a few bit operations and list links whatever the number of free blocks. Good fit (the least class that fits), so the big block at the top is split only when nothing smaller serves. A 16-byte header a block (the block before, the size and the free bit), payloads 16-aligned, 32 bytes the least block; a free merges with both neighbours at once; each region ends in a size-0 sentinel. `realloc` works in place first: a shrink cuts the tail off, a grow takes the free block behind (a Vec doubling over free space moves nothing).
- **The lock** (`ferros_rt/src/lock.rs`): a futex mutex over the kernel's WAIT/WAKE, the shape of std's own Mutex here: 128 loads of spinning, then the waiter sleeps until the holder's unlock wakes it. Nothing spins without end; a preempted holder costs the waiters only the wait. The thread registry uses it too. No kernel change was needed.
- **The arc**: grows as before (ARCS.md step 2), each grow joined to the last one's region; and gives back from the top (`ARC_SHRINK`) when the free block at the top of what it grew passes a cushion (ARCS.md, "ferros_rt gives back"). Never `ARC_RELEASE`: a hole in the middle of a native arc is never refilled.
- **No per-thread caches**: on Mahere's harness the heap now costs what the host's malloc costs (below), so they would add hoarding and a flush at every thread's end for nothing measured.
- **Tests and numbers** (`tools/rt-heap`, x86_64 Linux: `cargo test --release`, `taskset -c 0-3 cargo run --release --example bench`): the runtime's own tlsf.rs, lock.rs, layout.rs and alloc.rs by path, over Linux's futex and a fake arc whose given-back frames are unreadable. A shadow map checks that no byte is handed out twice (166 thousand blocks of 1 B-32 MiB at alignments to 64 KiB, the heap's lists and regions walked every 4096 operations); eight Mahere-shaped threads make 707 thousand calls over a growing and shrinking arc (9 grows, 4 shrinks, 174 MiB at the peak, 36 MiB at the end). One thread, a ring of 16 B-4 KiB blocks: the free list took 130 ns a call fresh, 135 µs at 20 000 free blocks and 187 µs at 50 000; TLSF 20-22 ns at all three, glibc 18-22 ns. Eight threads on four cores for 4 s: the free list's drawing thread made 8 frames (528 ms a frame in the heap), TLSF's 5720 (0.67 ms; 1.2 µs a call, all of it the lock under eight threads that do nothing else), glibc's (per-thread arenas) 56 thousand.
- **Mahere's frame harness** (mahere-device `examples/ferros_frames.rs`, 60 s at 1344 × 2992 under `taskset -c 0-3`, cells from the bucket each held back 10 s): the free list, frames of 0.4-0.9 s with 120-460 ms of each in the heap, 279 % CPU, 29 cells in by 55 s; TLSF, 0.1 ms a frame in the heap, 90 % CPU, 70 cells in; the host's malloc, 89 % CPU, 70 cells.
- **After a change to the heap**, every std app is rebuilt (Traps below: delete ferros-rt's fingerprint first).

## Traps met

- Under `relocation-model = pic` rustc reaches an extern static through a GOT entry — and the GOT entries are exactly what `relocate()` has yet to fix. `relocate()` finds its three linker symbols with PC-relative `adrp` in asm (`sys::pc_rel!`); the first hello faulted in the heap setup on an unrelocated `__bss_end`.
- cargo's build-std does not notice edits to a path dependency of std: after changing `ferros_rt`, clear `target/aarch64-unknown-ferros/release/{.fingerprint,deps}` of `ferros-rt-*` and `std-*` (or `rm -rf target`).
- `panic_immediate_abort` is a panic strategy now, not a std feature; `compiler-builtins-mem` must be in `build-std-features` or `memset` is undefined at link.
- The handle-guard pre-commit hook takes the better part of an hour over the 58 MB first commit of the std fork.

## The substrate, piece by piece (all 2026-10-27)

- **tokio** multi-thread runtime (`rt`, `rt-multi-thread`, `sync`, `time`, `macros`; no `net`, which needs mio and socket2 and a libc): `std/probe` ran 8 tasks over 4 workers with timers in 71 ms. Photon's sockets will be a ferros socket type over the `ip` server, not tokio's.
- **kete** over the kernel vault (`kete/src/ferros.rs`): the process's Store scope, every entry by the 32-byte address kete already derives, passed to the kernel as those bytes (SYS_STORE bit 5), values in 4 KiB pieces (staged writes, delete, list). The probe wrote a 10 KB value, read it back exact, listed, deleted. No `dirs`, no files.
- **getrandom** 0.2/0.3/0.4 custom backends in `ferros_rt` (`--cfg getrandom_backend="custom"` and the 0.2 `custom` feature from the program's side) — the kernel's entropy or an error, never the mixer.
- **fluor** `host-ferros` (`fluor/src/host/ferros/mod.rs`): the Android shell's twin over the display server's app surface (op 22, 16-bit gamma-2 working values from fluor's gamma-2.2 darkness bytes through one table) and the touch server's contact records (the first finger is the pointer; pinch waits for the input work). `std/fluordemo` draws text and counts taps in a 448 × 996 frame; spawn it with `--use display --use touch --dma app-surface --entropy`.
- **Memory**: `cachemap::POOL_BIG`, 512 MiB at G#A000_0000 in 2 MiB blocks (nothing in the device tree reserves G#9800_0000-G#C000_0000), a second buddy pool for arcs of 16 MiB and up (and small ones when the page pool is full); masked arcs stay in the page pool for their per-page W^X. The demo's 64 MiB arc (3.3 MB image + a 32 MiB heap by `--defsym __ferros_heap=`) is the first from it.
- **C in the graph**: `tools/std-build.sh` points the cc crate at `aarch64-linux-gnu-gcc` freestanding with `tools/std-sysroot/include` (string, stdlib, assert, stdio, inttypes, math, unistd, features: declarations only, the mem routines are compiler_builtins'), and the PQClean KEM suites build and run — ML-KEM-768 round-trips on the device in 572 µs. Crates that spell C types through `libc` (pqcrypto-internals, rav1d) take the fork at `/mnt/Harbor/Code/ferros-libc` (libc 0.2.183 plus a `ferros` arm of scalar types, no functions): `[patch.crates-io] libc = { path = … }` and `cargo update -p libc`. fluor's `icon` feature stays off on ferros until rav1d is tried through that fork.

## Photon on the device (2026-10-27, evening)

- `std/photon` builds Photon's library under a ferros main (fluor's ferros host, the spawn line `--use display --use touch --dma app-surface --use udp --store photon --ira --entropy`), with its own lockfile and patch table so Photon's own manifest, lock and config stay as its desktop and Android builds want them. `tools/photon-build.sh`. Photon's repo carries the `cfg(target_os = "ferros")` arms: every fgtw.org path answers that it does not speak to the server from ferros, the wave engine and the kept-wave decoders say no audio yet, the desktop modules have ferros answers in `platform/`, and the sockets are `platform::net::{UdpSocket, StdUdpSocket}` — tokio's and std's elsewhere, over the ip server on ferros (`platform/ferros_net.rs`, ops 1 SEND, 2 RECV polled every 2 ms, 3 INFO, 8 JOIN).
- **The image is 103 MB**, 81 MB of it read-only data. Only one piece is identified: vsf's x text codec Huffman table (`vsf/huffman_codes.bin`, 8.9 MB), the table the handle-to-identity derivation needs (`ihi` embeds nothing). The rest — blobs of about 27 MB, 12 MB and two more near 8.9 MB — is not yet attributed; fonts (Photon's multi-script Noto set, fluor's 10.7 MB emoji) and the camera database are the likely owners, unconfirmed. (An earlier draft called 55 MB of this the handle tables; that was an unchecked inference and wrong.) A release build shrinks the code, not these. Whether the handle codec belongs on the device is the owner's call (the no_std client kept it off).
- **Streamed spawn**: the kernel's staging slot is 4 MiB and its heap 22 MiB, so a std image goes straight into its arc: the bridge sends `spawn` Write pieces of 1 MiB — `[total][need][code offset][code length][piece offset][piece]` — the first allocating the arc (zeroed, from the big pool), then the usual Exec builds the process in place (`process::spawn_capsule_staged`, `build_from`). The gate verifies the Ed25519 signature in place (`oracle::gate_located`: the 64 signature bytes zeroed inside the arc, hashed, verified, put back): vsf's verifier copies the whole file first, and that copy killed the kernel on the first try. `FERROS_STREAM=1` forces the path for small images.
- **Photon Transport moved 215 KB/s** (477-byte packets, one at a time) until 2026-10-31: the bridge slept 1 ms after every packet. Without that sleep it moves **3.4 MB/s** (2 MiB in 0.62 s), so the 103 MB image takes about 30 s. The USB 2.0 link carries 35-40 MB/s; the next step is multi-packet transfers (a large receive buffer in place of one 512-byte TRB).
- The kernel now writes the last boot's end (fault ESR/ELR/FAR, panic number and text) into the flash log at service start (`diag log`), since the result block is cleared at boot and a reboot was otherwise silent.
- **Photon runs on the device** (the evening of 2026-10-27): the UI thread renders through fluor's ferros host (a 202 ms launch render, 111 ticks/s), 12 threads, the network thread on the ip server hearing the desktop and two other fleet devices over IPv4 and IPv6 multicast, its log echoed to the console, frames on the panel ("looks pretty damn good" — the owner). Behind it: the blocking socket shape (`StdUdpSocket`), no TCP port probe, no session file (tohu), no log or runtime directory, and a wake sender that queues background events for the frame loop.
- Still to do around it: the std Photon is an app a person stows, never part of the base OS (owner, 2026-11-04); the OS keeps the FGTW side itself as `payloads/fgtw` (the identity service, part of attest), which stays whatever Photon does. Stowing it needs a way to keep a 100 MB capsule in the vault, since the kernel's store path stages a value in its heap; the display shows the map and the app at once (the owner: a windowing manager is coming); PT at 215 KB/s makes every Photon iteration a 12-minute cycle.

- **Spawn:** `ferros-bridge spawn …/mahere.bin --name mahere --use display --use touch --dma surface --ira --store test --entropy` (and `--use gps` last, the person's choice). - **Ran** 2026-11-07: vault open, 20 built-in themes written on the first start (33 s through the kernel's store path), the first frame on the panel at 1344 × 2992 on the CPU raster. No map data yet: cells come only from the vault on ferros (no TLS here, and ureq has no transport over `ip`; the bucket answers plain HTTP too, so an HTTP client over ip's TCP would reach it).
- **Its cells over the network** (2026-11-11, the owner: "we have tcp and http so let's get the full meal deal wired up with mahere"): as on every other platform, the vault first and the bucket behind it, each cell fetched kept in Mahere's own domain as it comes, area downloads the same path. The bucket is reached over plain HTTP (`http://brobdingnagian.holdmyoscilloscope.com/mahere/cells`; no TLS here, and it answers port 80 as it answers 443). Mahere's side: mahere-engine `plain_http` (a GET over any byte stream, host-tested; `HttpStore`'s ferros arm) and mahere-ferros `net` (the stream: the ip server's client TCP, ops 4-7; the address from the DNS server ip's INFO reports, AAAA first then A, from UDP port 53055; four connections at once since ip's TCP was re-engineered the same day, the rest of its sixteen left to the device's own). No std::net: std's sockets stay `unsupported`. Every wait is a held receive (ip's ops 2 and 6 with a wait byte, added the same day), never a poll; the deadlines are DNS's second a try and 32 s of nothing on a connection. The kist wants `udp` as its eighth slot (tools/mahere-kist.sh), after gps, so the older slots keep their numbers; a development spawn adds `--use gps --use udp` in that order. Each fetch is said on the console (`mahere: fetch base/<cell>.vsf?e=8: 200 N bytes in M ms`, or `failed in M ms: why`), the host's address once (`mahere: <host> is G#… (M ms)`), and at start whether the network is there (`mahere: the network at slot 8; …` or `mahere: no network: …`). Measured from the desktop over the same client: a depth-0 base cell is 1.6 MB, its terrain 136 KB; ip's 4 KiB receive window a connection was what bounded a fetch on the device (a window a round trip), so ip's TCP was re-engineered that evening (WIFI.md "Client TCP for throughput"): a 1 MiB window with scaling, out-of-order segments kept and SACKed, congestion control, sixteen connections, and a TCP receive answering up to 256 KiB, which Mahere's reader asks for whole; each connection's measures are a console line from ip when it is freed (`ip: tcp A#… port A#80 closed both ways: in A#… bytes, …, peak A#… MiB/s, …`).
- **Found with it:** the grants page's handle table (2026-11-03) moved the count to G#200 and the tokens to G#204 + 32k, but ferros_rt's `grant_count`, kete's store search, fluor's ferros host and Photon's ip slot still read the old offsets: std found no entropy grant (rand's `thread_rng` panicked), kete no store, fluor no display. All four fixed. Photon's documented spawn line above is stale too: `--dma surface` (not `app-surface`) and no `photon` store scope since 256dc23.
