# Windows on ferros

The design for putting more than one thing on the glass: the map, an app in front, the keyboard over it, and the attest screen over everything. Written 2026-10-27 after the owner called the present path "a glitchy hot mess". The owner decided on 2026-10-27: every window is full screen for ownership and layering; each app gets its own full-screen buffer to draw as it wishes, and the display draws them in order, frontmost first; an app in front lives in a full-screen circle tangent to the screen's top and bottom, the four corners left for the system (clock, signal, navigation). How widgets fit is still open. "Built" below says what runs.

## What goes wrong today, and why

The present path is one slot. The display server has one `APP` (a rectangle), the kernel has one 32 MiB `app-surface` region granted to every app, and every process that wants touches polls the touch server. Each glitch traces to that:

1. **The map's frames reached the glass under an app.** The map kept drawing (its dashboard redraws every second, a bridge-spawned app never stopped it), and each of its frames went into one of the four dither phases while the app held the other three. The 10 Hz flips then showed both. Fixed 2026-10-27: `publish_next` publishes nothing while an app is in front, and op 23 already repaints the map in full.
2. **Every app shares one surface.** Photon, Ramps and Hive all get the same `app-surface` block. Two apps alive at once draw into the same memory, and a keyboard over an app has nowhere to draw.
3. **The display cannot tell its clients apart.** `recv` hands a server a reply token and nothing else (KERNEL.md: no PID, no ambient authority). Any client's op 22 takes the screen and any client's op 23 ends whatever app is in front. Fixed 2026-11-12: the display asks the kernel whose surfaces a caller holds ("Whose surface" below).
4. **A dead app keeps the glass.** Nothing tells the display that a process ended, so its last frame stays up and the map waits for an op 23 that never comes. Restarting the display drops a live app's frame instead.
5. **Touches go to everyone.** Each process polls the touch server and sees every finger, so the map and the app both act on one tap. The map now stands aside while the display says an app is in front, but that is a convention, not a rule. A HELD poll also takes about 15 ms (measured 2026-10-27), so polling clients see touches at about 66 Hz.
6. **The text op assumes a full-screen surface.** Op 26 indexes with the panel's width, while op 22 lays a frame out at its own width. Fluor's centred half-size frame and text cannot be used together.
7. **Op numbers collided.** The frame wait took op 24 on 2026-10-24, which was already text. Every text call since drew nothing. Text moved to op 26 on 2026-10-27.

## The model

On the phone, apps are places (SHELL.md), not overlapping windows. So the window manager is a short stack of layers, not a desktop:

| layer | what | how many |
|---|---|---|
| 0 deck | the map | one, always there |
| 1 front | the app in front, full screen | at most one shown; others alive behind it |
| 2 input | the keyboard, docked at the bottom | one, while the front app wants text |
| 3 system | attest (ahau), the power-key states | one, above everything, takes all input |

A pixel comes from exactly one layer, because the layers do not overlap where they are opaque: the keyboard's band is the keyboard's, the rest is the front app's. So composing is a list of row spans per layer, not blending. That keeps the one-table, dither-at-full-precision publish the display already has, run once per span.

## What the kernel has to add

Three primitives, each small and each useful beyond windows:

- **Badges.** A capability to an endpoint can carry a 64-bit badge, set by whoever grants it (the spawner) and returned by `recv` beside the message. The map spawns an app with a display capability badged for that app, so the display keys windows by badge. A badge is not a PID: it names a capability, and only the granter chooses it. This is the seL4 way, and it fits KERNEL.md's "no ambient authority".
- **Death notices.** When a process ends, each endpoint it held a badged capability to receives one kernel message: the badge, and that it is gone. The display drops the window, the input routing drops its fingers, and the map learns that the app ended. This replaces polling op 5 for an app that has left.
- **Shared regions.** KERNEL.md already plans this: "Shared memory regions: explicit cap grant, both parties hold caps." At spawn, the spawner asks for a fresh surface region from a surface pool, granted to the child, with the same region granted to the display under the child's badge. No app can see another's pixels, and the display reads only the regions it holds.

## Knobs (the owner's picks)

1. **Caller identity:** badges set by the granter (recommended), or the kernel stamping each message with the sender's spawn epoch. Badges keep the kernel out of naming. The epoch is less code but is a PID by another name.
2. **Surface memory:** regions from a pool at spawn (recommended), or the display server owns one big pool and hands apps offsets. The second needs no kernel work, but every app can read and write every other app's pixels, so attest could be spoofed by an app.
3. **Pixel format in surfaces:** 64-bit working values (today: R, G, B as gamma-2 Q14 plus a no-dither bit) or 32-bit. A full-screen 64-bit surface is 32 MiB, and the pool has to hold one per live app plus the keyboard's band. 32-bit (10:10:10 gamma-2 plus 2 flag bits) halves that, at 10 bits a channel before the dither instead of 14. Since 2026-11-12 a third: `BAKED` (format 2), the panel's own codes in the same 64-bit layout (COMPOSITOR.md "Baked"), which the display only dithers; formats 0 and 1 it bakes every frame.
4. **Who routes touches:** the display server (recommended) or the touch server with a region table. The display knows where every layer is. With routing there, the touch server has exactly one client and apps block on a "next input" op instead of polling, which also removes the 15 ms HELD poll from every app.
5. **Composing:** software spans through the existing publish (recommended first), or DECON's hardware windows, one layer per plane. Hardware planes cost nothing per frame, but the temporal dither and E's gains are software, so each plane would still need its own publish. Measure the software path first.
6. **The keyboard's place:** it overlays the bottom of the front app and the app is told its visible height (recommended), or the app's frame shrinks and it redraws. The first never resizes an app under the user. The second is what Android does, and it reflows text.
7. **Background apps:** an app not in front keeps running and keeps its surface (recommended, so returning is instant), or it is suspended and its surface released. The pool size decides how many can stay.

## The protocol, once those exist

Per window, keyed by the caller's badge:

- **show** `[x][y][w][h]`: this window's frame, from its own surface, laid out at its own width. Text into the window's surface uses window coordinates.
- **done**: this window leaves. Only the window's own badge can end it.
- **want text** `[on/off]`: the front app asks for the keyboard. The display raises layer 2 and tells the app its visible height.
- **next input**: blocks until a contact or a key for this window arrives, in window coordinates. Keys from the keyboard arrive here as bytes, so an app never talks to the keyboard directly.
- **frame wait** keeps op 24.

The map is a window like any other, on layer 0, with the camera ops it has today.

## Built (2026-10-27)

- **Surfaces.** Four full-screen surfaces of 32 MiB at G#CA00_0000 (cachemap SURFACES), between the display's canvas and the debug snapshot. The display holds the `surfaces` region; an app gets one surface of its own at spawn: the map passes the region (SYS_SPAWN turns it into one fresh surface) and `bridge spawn --dma surface` asks for one. The old shared `app-surface` (over the modem image at G#C000_0000) is gone.
- **Death notices, without messages.** Bytes 8-11 of every process's preferences block hold each surface's generation (0 free). The kernel frees a surface when its process ends or is killed (`diag kill <name>`), and the display drops a window whose byte changed on its next pass. Badges are not built: the window is named by its surface's base, which the display checks. There is no per-process memory isolation on the daily processes yet (they run native; SANDBOX.md's masking and handles exist and they migrate one by one), so nothing stronger would hold until they do.
- **Whose surface (2026-11-12).** The GPU's isolation work found that the display checked a base named a surface but never whose: any app could show another app's surface as its own window, draw text into it, read its events, raise it, or send it behind. Now the display asks the kernel, with the call's reply token before replying (SYS_CALLER, ferros_sys `caller`), what the caller holds: the surfaces in its capability table (its own `surface-k`, or a region holding one whole: the display's and the GPU service's `surfaces`), whether it holds Settings, whether it is a kist. An op that names a surface (22 show and its mailbox's buffer, 23 done, 26 and 29 text, 27 whose point, 62 events) needs the caller to hold it; front (59), and full screen (43), behind (60) and a key (61) on the app in front, need the caller to hold that window's surface or to be the system's window management (the Settings holder: the map, the attest screen). Refused, the reply's status is 4 (`window::NOT_YOURS`; op 27 answers "not yours"), and the console says so at the 1st, 2nd, 4th, 8th refusal and on. The check is where the op runs, so one inside a batch or a flight is refused as well; the display's own runs (a frame replayed, the quick row's capture) hold nothing and name no surface. On a kernel from before the call every op that names a surface is refused, never trusted to the client's word: deploy the kernel with the display.
- **Whose level (2026-11-12).** A show's level byte was the client's own word, so any client could pick any level: a kist could put its window in front of the attest screen or the keyboard and pass for them. Now a level above the app's (1 input, 2 the system) is the system's alone: the caller must hold Settings and not be a kist, by the same SYS_CALLER answer as "Whose surface" (`system` and `level_not_theirs` in payloads/display). The system processes that show there are the attest screen (ahau, level 2, its keyboard drawn in its own window; init hands it Settings) and the map (which holds Settings, though it shows no window today); a separate system keyboard at level 1 would hold Settings the same way. Every other caller (a kist, Hive, Ramps, fluor's ferros host, the GPU's test picture, wintest) shows at level 0. A show above its level is refused, not lowered to the app's: the reply's status is 4 (`window::NOT_YOURS`), the window is not shown, and the console says "a show at level A#2 from a kist, above the app's: refused" at the 1st, 2nd, 4th, 8th refusal and on (its own count). Refused where the op runs, so inside a batch or a flight as well. A kist cannot be handed Settings (the kernel's `kist_object`), and the check names the kist bit anyway, so the rule holds whatever a kist is handed later.
- **The windows' owners' bell (2026-11-11).** Mahere, a kist, was ended from outside (`diag "kill Mahere"`) on the Pro; its window stayed in the display's table, op 5 kept saying an app was in front, and the map ignored every gesture but the corners until the display was restarted. Now the kernel pushes the owners: SYS_BELL source 9 (`BELL_SURFACES`, for the holder of the `surfaces` region alone) writes into a word of the display's the four surfaces' live generations (byte k surface k's while the process it was given to is alive and not ending, 0 otherwise, from the kernel's own table) and a change count above bit 32, as a surface is given (once its process is in the table) or freed (every end: exit, fault, panic, `diag kill`, a relaunch), waking the display's `reaper` thread asleep there. The reaper wakes the render thread, whose next pass drops every window shown under a generation the bell and the preference byte no longer both hold. Op 5's byte 12 is no longer `APP` but "a window up whose owner lives", from a copy of the windows' generations and the bell, answered by the receive thread, so the map hears of the end at its next op 5 whatever the render thread is doing. Op 22 reads the generation once (read twice, a process ending between the reads left a window kept under generation 0 that nothing ever dropped) and refuses a surface whose owner is gone. The kernel also gives back a surface taken for a spawn that is then refused, and `kill` passes over a process already ending. No timer anywhere: a process's end is the only thing that rings.
- **Composing** (as built; since 2026-11-12 nothing is cut to the circle, "Drawn under the controls" below). Each row frontmost first (level, then the last shown): a pixel comes from the first window whose rectangle covers it and whose bit 63 (see-through) is clear, branchless; black behind them all. Then the glass's shape, from one plan per screen size (`plan_glass`, owner 2026-11-02: "maintain a global compressed mask since most will be opaque for the OS in general"): per row the chrome columns from each side (outside the circle, which is tangent to the bottom of the camera cutout and the bottom of the screen since 2026-11-02), the masked columns from each side (outside the screen's own edge, over the chrome) and the row's antialiased pixels, the circle's then the edge's, each with a coverage and a hairline alpha. The publish path does no geometry: it copies the runs and blends the listed pixels. The circle's hairline is one pixel wide on the radius, its profile (1 - t²)² across it (E grey one stop below the theme's ring on release builds, bright orange on development builds), planned from one crossing per row and the band's pixels. The edge is Photon's window on Android glass: a superellipse corner inside the glass's arc (fluor's glass corner rule at the panel's radius, 80 px on husky), the top-left and bottom-right corners twice the top-right and bottom-left, from fluor's crossings walk (`paint::edge`, shared with Photon's chrome): one antialiased pixel per axis on the curve, the hairline on the outer pixel and its complement on the inner one. Outside the curve the mask: black on release builds, where the edge hairline is black too (Photon's release rule on Android), the hairline's orange one stop darker on development builds. Then the one table and the dither, as before.
- **Ops.** 22 show `[x][y][w][h][base u64][level]` (then optionally `[format]`, `[changed x y w h]`, `[mode]`), 23 done `[base]`, 26 text `[base][x][baseline][size][value][utf8]` (synchronous), 27 whose point `[base][x][y]` (answered by the receive thread: one read of the hit map since 2026-11-11, COMPOSITOR.md "The hit map"). ferros_sys::window wraps them; fluor's ferros host speaks them.
- **The corners (2026-11-03).** Three circles in each corner (owner: "tangent on all sides, three for each"), solved from the glass exactly as `plan_glass` drew it (its fat and small corners, glass mode's diagonal pair) and the app's circle: the middle one maximises the clearance to the nearer of the two, so it touches both; each side one sits where the two clearances are equal and also equals its distance to the middle circle's edge, so it touches the glass, the app's circle and the middle one. Clearance to the glass is signed (outside the glass on a point's own row is none). Solved once per screen size and cached; a moving or resizing app circle needs the cache keyed on the circle and a Newton step from the last solution instead of the grid. Indicators up top, navigation at the bottom (owner, 2026-11-03): top left the clock (the time in the device's base), battery along the top, USB down the edge and GPS chained past the battery (tangent to the glass, the app's circle and the battery's); top right cellular, WiFi and Bluetooth the same way along the top and NFC down the edge (2026-11-11, both boards: the spot by the camera stays open as the quick row's doorway, QUICK.md); bottom right the deck, the rest of the bottom blank for navigation. IP is no radio: its latency and loss are the links' measures.
- **Link measures (2026-11-03).** No signal bars, and no one number for a link (owner: "frequency, bandwidth, speed, latency, flavor, packet loss ... RSSI, VSWR ... definitely not quantized to 5 bars"). Each driver publishes up to eight tagged measures (kernel SYS_STATUS 27, SYS_FACTS 33-80, eight words a link: modem, pcie1, bt, nfc, gps, usb; `ferros_sys::measure`): a word is the kind in bits 48-63 and its value, signed, in its own unit below (milli-dBm, milli-dB, kHz, bit/s, ns, ppm, thousandths for VSWR), all ones an empty slot, and a new measure is a new kind. The kernel keeps the words and reads none. A circle shows its name and each measure as a line in its unit, each line as large as its own chord allows. WiFi publishes RSSI, SNR from the noise floor, the centre frequency and width from the chanspec, the PHY rate and the transmit loss over two seconds (WLC_GET_RSSI, WLC_GET_PHY_NOISE, chanspec, WLC_GET_RATE, WLC_GET_PKTCNTS); USB its signalling rate; the modem its state and technology (its name shows LTE or NR), its signal waiting on IND_SIGNAL_STRENGTH (G#0906) decoded against Android's readings of the same moment, never guessed. VSWR has a kind; no driver measures it yet. Everything else a link knows, its names and addresses, and its knobs are on its page in settings (docs/RADIO-CONTROLS.md: tracks, the detail document behind Settings, the control blocks).
- **Flavours.** Each radio its colour, picked in VSF RGB and scaled to the grey's light by VSF's photopic weights: cellular amber, WiFi sea teal, Bluetooth periwinkle, NFC lime, GPS dusk magenta. The ring full when connected, a stop darker when up without a link, grey when the driver does not run; the name in the flavour, the measures in plain ink. Taps are not built.
- **Touches** still go to every client; each asks op 27 on a finger down and drops fingers that are not its own. Op 27 reads the display's hit map (2026-11-11, COMPOSITOR.md "The hit map"): a window owns the pixels where it is frontmost and not see-through, inside the circle, and never one the system holds (the corners, the quick row and what lies behind it while it shows); routing through the display can read the same map. Two levels: the display's map picks the window, the app's own fluor map (`HitId`) picks the widget.
- **Measure** is op 28 (2026-11-01): `[size u16][utf8…]` → `[0][width u32, quarter pixels]`, synchronous. It was op 27 for a day, which is "whose point"; the same collision as op 24.
- **Centred text** is op 29 (2026-11-01): op 26's layout with x the centre of the text's ink, left to right; the keyboards' labels (`window::text_centred`).

- **The system level.** The attest screen (payloads/ahau) is the first window at level 2: init starts it before the map, so nothing else shows until the person attests. No caller but the system's may show there ("Whose level"). Started by init through SYS_SPAWN, it got its own surface from init's `surfaces` grant, which exercised that path.

Verified on the phone by reading the dither phases back over USB: Hive alone; Ramps in front of Hive, cut to the circle; Ramps killed and Hive back; fluor's half-size frame over Hive with Hive around it.

## The layer stack (2026-11-02)

The owner's direction: "we will need to support full compositing. How do we maintain a layer stack and update slices?" and, on blend modes, "do it with blend modes". Built the same day in the display server (`layout_build`, `fold`, the span walk in `publish_app`); the geometry moves to fluor next so Photon's own stacking can share it.

- **A layer** is a window: its surface, its rectangle, its level and the order it was shown (the stack order, as before), its pixel format, and a mode byte on the show op (`ferros_sys::window::show_full`): bits 0-2 the blend mode in fluor's order (Normal, Multiply, Screen, Add, Subtract, Overlay, Darken, Lighten), bit 3 `OPAQUE`, the window's promise that none of its pixels is see-through.
- **Bands and spans.** The windows' top and bottom edges cut the screen into bands of rows; within a band every row is laid out alike, so the left and right edges cut it into spans. A span's chain is the windows covering it, frontmost first, cut after the first opaque one: nothing behind an opaque window is read. At most four windows, so at most nine bands of nine spans. The layout is rebuilt when a window is shown at a new place, level or mode, when one is done, and when one dies: never per frame.
- **Slices.** A show carries what changed (`show_changed`); each dither phase keeps its own dirty region, the union of what it owes. Publishing a row walks its band's spans clipped to the dirty columns: an empty chain is black; one opaque working window is a copy; working windows in Normal are the branchless select (see-through is the bit alone); anything else is the fold.
- **The fold** is fluor's `Blend::under` front to back on the working values: the composite so far carries a transparency (Q14 in bits 49-62 of the working pixel, 0 opaque, the see-through bit 16384); each layer behind adds the mode's value of (composite, layer) by what its alpha fills of what was still transparent, and the transparency multiplies. The mode applied when a layer is folded is the mode of the layer above it: a window's mode says how it sits on what is beneath. A fluor surface (`G2T16`) keeps its alpha through the decode, so a half-covered pixel of a fluor window really shows the window behind; a working surface declares only the bit. What is still transparent at the end is over black.
- **Cost.** Nothing where no layer uses a mode or an alpha: the copy and the select are what the server did before. A moded or alpha slice is a few integer operations per channel, on that slice alone. A moded window can never become a hardware plane later (DECON blends with alpha only); the rest of the model does not care.
- **The glass's shape** (the edge and the camera hole's knockout, `plan_glass`; the circle too until 2026-11-12) applies after the spans, as the last layer of all.

## The corners: controls and gestures (proposed 2026-11-02, the owner sleeping on it, nothing built)

The owner's question: "controls. could be zero, could be a hundred. back, recents, home, search... should we? gestures?" The proposal is close to zero, with the four corners doing what is left, because the map already is most of it.

**What the map already is**

- **Home** is the map (the deck since 2026-11-12). An app is one of its circles opened in front; leaving the app is closing the circle, and the map is there with no transition.
- **Recents** is the map too: the circles that are open look open. A task switcher would be a second, worse map.
- **Search** is typing on the map: the keyboard is shape writing, so writing a name on the map filters its circles. No button, no search bar.
- **Back** belongs to the app. Android's system back exists because apps could not be trusted to draw their own; a fluor app draws its own way back. The exception is APKs (decision 0).

**Why the corners, and only the corners**

The corners outside the circle are the system's by construction: no app surface ever covers them, so a touch there can never be stolen by a fullscreen game or a misbehaving app. That makes them the escape hatch every OS needs, without a button. Each corner does the one thing it shows:

- Top left, the clock: time, alarms, the zone.
- Top right, the radios: connections, WiFi join, airplane.
- Bottom left, the battery: power, brightness.
- Bottom right: the deck (named home until 2026-11-12). A tap from anywhere and the map is there. The only navigation control, and enough, because the map is home, recents and search at once.

Four corners, four things, nothing to learn. Hardware stays what it is: power wakes under the proximity gate, the volume pair is the killswitch chord and volume.

**Gestures**

Geometric ones only and nothing timed (the standing rule: no long press, no double tap, no swipe that depends on speed):

- Pinch an app down to close its circle: the deck by gesture, the same operation as the corner.
- Two fingers turn a circle over for its back and settings, as the map does now.
- Drag to pan the map.
- A drag that begins outside the circle is the system's by the same ownership rule: room later for an edge slider (volume, brightness) no app can collide with.
- No edge swipes from the glass edge: they collide with the screen's own mask and the apps' content, and they are the gesture most often triggered by accident.

**Decisions**

0. **APK back.** Android apps need a back signal. Either bottom right means back while an APK is in front and the deck from an APK's top screen (what Android's gesture ends up doing), or the APK runtime draws a small back control inside the APK's window and the corner stays the deck everywhere. Proposed: the second, one meaning per corner.
1. **The deck as a tap, a pinch, or both.** Proposed: both; they are the same operation and neither is timed.

**Build order, once decided:** the bottom-right tap (one corner hit test and a done op), then the pinch, then the other three corners as their pages exist (ATTEST-UI.md's indicators give the top right and bottom left their faces first).

  - **62 `events [base u64][seen u32]`** → [0][count u32][state u8: bit 0 behind][k u8][k events u16]: the caller's window's events after `seen`, held by the receive thread until there is one (a doorbell, never a poll; display events.rs). An event is its kind in the high byte (1 behind, 2 front, 3 key, 5 open at: a note the person opened, NOTIFY.md "A tap"; 4 is the bake's, COMPOSITOR.md "Baked") and a key's usage (or the note's number) in the low one; the last sixteen are kept, and the state byte says where the window stands whatever was missed. A surface's events belong to the generation it was given under: a new owner starts from nothing.
  - **67 `open at [note u8]`** → [0][surface][generation], or [3]: the person opened that note of the kist in front, `EV_OPEN_AT` to its window (`window::open_at`; the deck's, docs/NOTIFY.md).
  - **66 `helm note [icon u8][count u16]`** → [0], or [4] from a caller that is not the system's: the Deck button as the deck's summary, the latest note's source icon and how many wait in the resting view (`window::helm_note`, docs/NOTIFY.md "The Deck button"); answered by the receive thread.
  - **43 `full screen`** now switches the app window in front's own flag (`Win::full`, kept while it is behind), [3] with none; `FULL` follows the app in front, so the deck always has its bars. In full screen the console and the quick row are gone, drawn nowhere and on no pixel of the hit map; the helm's wedges stay the system's, undrawn (above). Until 2026-11-11 the console's rows showed while the bars on the glass held any of the quick row, pulled from the doorway, so its circle could switch full screen off; deck's swipe does that now.
- **Which kist is which window.** The kernel answers a kist launch for a kist already running with `RUNNING_ON` | surface << 8 | generation (process.rs `kist_request`); init passes it on as RUNNING with the two bytes (ferros_kist::launch::RUNNING); the map raises that window (op 59). The map keeps the kists it brought to the front, most recent first, by capsule, for back's flip; a kist that ended since is launched again by the flip.
- **The app's side** (fluor's ferros host): a thread holds op 62; behind, the frame loop draws nothing and reads no touches, asleep until the display or the app's own threads ring, taking in its user events and its tick as they come; the app hears `Focused(false)` and `on_focus_changed(false)`. In front again: focus back, `on_window_shown`, the touches queued meanwhile dropped (they were made on other windows), and the next frame drawn whole. Escape arrives as a key press and release, `NamedKey::Escape`.
- **Deck's turn** (map `deck_turned`): the fit's zoom as a function of the turn has period a half turn; sampled 64 times across the half turn centred on the camera's own, then golden-section steps between the best sample's neighbours, and the flight's spring turns the short way. Where the zoom limit caps every turn alike, the camera keeps its turn.

## The keyboard (2026-11-12)

Kists had no keyboard: Photon's handle field on the 8a showed a caret and nothing to type with, because the honeycomb keyboard lived only inside the attest screen.
Now any kist in front can ask for it, and the attest screen's own keyboard types for it.

- **Who draws it.** The attest screen's process (payloads/ahau) after attest, the one that already stays as the keyboard for words the identity service wants typed. Not a process of its own: the display has four surfaces, and ahau already holds two (its window and the keyboard's back buffer) for its whole life, so a separate keyboard beside Photon and Mahere would leave none (Mahere, Photon and ahau fill all four today). The keys, their boards, the back buffer and a key lit at its press are the attest screen's own code (`light`, `show_board`, `prepare`), shared, not forked; Hive stays the honeycomb's test app. A device unlocked at boot shows no attest screen, and ahau used to end there; it stays now, straight to the keyboard, as it does after `diag "restart ahau"` on an attested device.
- **Where.** A window at the input level (level 1, above every app, below the system's), from the keys' top to the screen's bottom, docked over the app in front, whose frame never resizes for it. Opaque: the gaps between the keys that the attest screen's words show thru are black here, so a finger between two keys is never the app's (the hit map gives a see-through pixel to the window behind it). The keys untinted: the rainbow stays the attest screen's own. The bar's left key puts it away ("hide", `Msg::KeyHide`). No shape writing yet: a tap types a key, at its press, as on the attest screen.
- **Who it types for.** Only the app window in front that asked for it, never another, and only while it stays in front. The display decides, the keyboard never names a window: it holds the input level, the text goes to whichever window the display has as wanting text, and an app never talks to the keyboard. Checked by the display's caller test (SYS_CALLER, "Whose surface"): asking for the keyboard needs the window's own surface; typing, the watch and putting it away need the system (Settings, not a kist).
- **When it goes.** The field loses focus (the app lets it go), back's tap (the Escape is the keyboard's then, not the app's: back's first tap puts the keyboard away, the next goes up a page, as on Android), the keyboard's own key, the app behind (deck, another kist in front, a flip) or ended. The display enforces it: a show at the input level while no app wants the keyboard is refused, and an input window up when the want ends is kept behind until one asks again.
- **The app's field above it.** The window that wants text is told the rows the keyboard covers from the screen's bottom (`EV_INSET`) as it comes, moves and goes, and 0 when it goes, so it keeps its field above them. fluor's ferros host turns that into `FluorApp::on_keyboard_inset` (rows of the app's frame, from its bottom); an app that does not take it is covered.
- **Ops** (`ferros_sys::window`):
  - **68 `text wanted [base u64][on u8]`** → [0], or [3] for an on from a window that is not the app in front: the app's window wants the keyboard, or no longer (`text_wanted`). [4] (`NOT_YOURS`) for a surface that is not the caller's.
  - **69 `keyboard watch [seen u32]`** → [0][count u32][wanted u8], held by the receive thread until whether a window wants the keyboard changed past `seen` (a doorbell, display keyboard.rs; `keyboard_watch`). The system's alone.
  - **70 `type [usage u8][utf8…]`** → [0][surface][generation], or [3] with no window wanting text in front, [1] for text past `PIECE` (64 bytes): usage 0 and the text (`EV_TEXT`), or a key's USB HID usage alone (`EV_KEY`: enter G#28, backspace G#2A), to the window that wants the keyboard (`type_text`, `type_key`). The system's alone.
  - **71 `keyboard away`** → [0]: no window wants the keyboard until one asks again (`keyboard_away`). The system's alone.
- **Events with a payload.** Kinds from 6 up (`PAYLOAD_KINDS`) carry bytes: the event's low byte is their count, and op 62's reply carries them after its events, in the events' order (`[0][count u32][state u8][k u8][k events u16][payloads]`). 6 `EV_TEXT`, the text typed (UTF-8, at most `PIECE` bytes); 7 `EV_INSET`, two bytes, the rows covered (u16, little-endian). The display keeps the last `EVENTS × PIECE` bytes beside the last `EVENTS` events, so every event it still holds has its payload whole. A reader with the old buffer (the events alone) is cut before the payloads and reads its events as before; a reader steps over a kind it does not know by its length.
- **The app's side** (fluor's ferros host, fluor branch `keyboard`): after each frame's show it asks `FluorApp::wants_keyboard` (the Android host's one-shot ask, which Photon already answers as a field gains or loses focus) and sends op 68; a wish made before the first frame waits for it, so the window is in front when it asks. Text arrives as `Event::Ime(Ime::Commit)` and enter and backspace as key presses and releases, in the order typed. The text never goes to the console: the host says how many bytes came, never which.
- **Verified on the 8a** (2026-11-12, injected taps): Photon (fluor `keyboard`) asked as its handle field took focus ("the keyboard asked for (the display took it)"), the keyboard came up over it and Photon was told it covers 634 of the panel's 2400 rows; h, i, v, e typed "hive" into the field, each once; delete took a character; back's tap and the keyboard's hide key each put it away with Photon still on its handle screen (no Escape reached it); a tap on the field brought it back; deck sent Photon behind and the keyboard with it, the map bare. ahau killed and started again came straight up as the keyboard for the field still wanting it, and its end told Photon the rows were none. Photon does not take the inset yet (`on_keyboard_inset`): its handle field sits above the keys anyway, a compose bar at the bottom would not.

## Drawn under the controls (2026-11-12)

The owner: "Should we draw under the controls?"; then, to the proposal below, "Agreed. Build it!"

Until then a kist's window was cut to the app's circle (tangent to the camera cutout's bottom and the screen's bottom, wider than the glass), and the corners outside it were the console's and the helm's, drawn over black.

- **The window fills the glass.** Nothing cuts a window to the circle: the display composes each row of the windows to the glass's edge, then front to back in front of it the glass's edge and the camera hole's knockout (both kept), and the bars, the console's circles at the top and the helm's wedges at the bottom (display `publish_app_rows`). The glass's plan holds no circle any more (`plan_glass`: the edge and the hole alone), so the publish blacks out no corner and takes no circle's coverage.
- **Full screen** is only the controls hidden: the console gone, the helm undrawn but live ("The helm"), the window as it always is now.
- **The circle is the kist's safe area**: where it keeps its own buttons and text, since the corners are always covered by the system's controls. The display tells each app window (level 0) its safe area as an event, `EV_SAFE` (ferros_sys `window::EV_SAFE`, kind 8, a payload kind like `EV_INSET`): 13 bytes, the circle's centre x and y (i32) and radius (u32) in 256ths of a pixel of the window's own pixels (its top-left corner the origin), then a byte, `SAFE_TOP` (1: the glass outside the circle above its centre is the system's) and `SAFE_BOTTOM` (2: below it). A point is the window's to use inside the circle, or outside it on a half whose bit is clear. Told when it differs from what the window was last told under its generation (`safe_follow`): at its first show (op 22) and as its full screen turns (op 43, and whenever the windows change), so 3 with the controls up and 2 in full screen, where the console's rows are the window's and the helm's wedges still the system's. The keyboard stays `EV_INSET`'s, apart from it: an app keeps its field above the keyboard and its controls inside the circle.
- **fluor** (branch `safe-area`): `FluorApp::on_safe_area(SafeArea)` (host/app.rs: `cx`, `cy`, `r` in the frame's pixels, `top`, `bottom`, and `contains(x, y)`), default ignored; the ferros host reads `EV_SAFE` from the held op 62 and hands it on, the frame drawn again. No other host calls it (Android unchanged: its frame is all the app's; Photon reads Android's own window insets for its orb).
- **Mahere** (branch `ferros-safe-area`, off `ferros-gpu`) centres its view on the circle the display tells it (`App::on_safe_area`; mahere-engine's `set_view` may now be called again, the view kept as three atomics, and the GPU frame's key holds it). It still works the circle out at start the display's way (`place_view`), so the first frame does not jump and a display from before `EV_SAFE` gives the same.
- **Photon** drew the desktop window's controls strip (minimise, maximise, close) in the top right on ferros, cut away with the corner until now: std/photon turns it off at start as Photon's Android build does (`DEBUG_SKIP_CONTROLS`). Its orb, the connectivity indicator in the top left, now shows under the clock's console circle; it needs Photon itself to move it into the safe area (`on_safe_area` to `DefaultChrome::set_orb_insets`, as its Android build does from the status bar's height), the owner's call where.
- **Legibility.** The console's circles have their own bodies, opaque. The helm's wedges are an eighth black, so over a bright kist the Deck ring and the Back arrow each get a dark glow behind them (display `helm_draw`): a layer of black at its own α, under the mark (and the Deck's note), three quarters hugging the stroke and nothing a quarter of the button's radius past it, falling off in log distance as the theme's glows do (each octave of the squared distance from the stroke's outer edge), on the C∞ step (`draw::bump_step`), so neither its start nor its end has a kink. Over black it is black on black; over the deck's wallpaper it shows as a soft shadow round each mark.
- **The circle's hairline** was already gone from a kist (owner, 2026-11-09: "Circle idea and alignment stays, just needs to be invisible"); with nothing cut to the circle it stays gone, and the display's `hairline()` with it. The deck's own open circle keeps the map's hairline (map `LOOK`), and the deck's look (the settings circle, the kist circles, the plane under the bars) is unchanged: the deck was never cut to the circle.
- **Touches** are unchanged: the system's ids (the console's zones and the helm's wedges) are written into the hit map in front of the windows, every pixel outside the circle, so a kist gets only what is inside its zones; in full screen the console's rows are the kist's and the helm's wedges the system's, as before.
- **Opening and closing.** A kist's window has no flight of its own (a tap on its circle launches it or brings its window to the front, a cut; KISTS.md's flight into the circle is not built): it appears whole, to the glass's edge. The deck's flight (COMPOSITOR.md, op 45 and 46: the settings circle, a kist's question or why it stopped) is the map's own region and unchanged.
- **The system's windows** (the attest screen at level 2, the keyboard at level 1) are not told: they lay themselves out in the circle by `active_circle`, and their corners now show their own pixels (black, but the attest screen's green when bound) under the bars.
