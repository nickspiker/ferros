ferros's UFS driver for Pixel 8 (husky/zuma/Tensor G3) is **proven correct but the device won't link**. This blocks the vault/manifestus storage path. Full trail is in the repo at `ferros/UFS.md`; this is the one-line state + the non-obvious conclusion.

**State:** `full_init()` (HCE reset → M-PHY cal → DME_LINKSTARTUP) fails — the flash device is silent at link-startup (`MAXRXHSGEAR=0`, `LS_RES=1`, zero error codes). Exhaustively verified CORRECT on the host side: PMA cal (register-diff), PCS cal (readback F6/79/02), PLL locks, refclk running, all clocks on, init sequence matches the core `ufshcd.c` (cloned to `/mnt/Harbor/aosp-common`). Found+fixed a real pinmux deviation (gph5-0/ufs_refclk_out was function 1 not 2) — didn't fix it. Device reset via `HCI_GPIO_OUT` is a confirmed no-op on husky (but Linux uses the same no-op reset and succeeds).

**Why static analysis is exhausted:** bootloader RE is a dead end — pbl/bl2/abl (FBPK stages extracted to `/tmp/stg_*.bin`) only do UFS *transfers*; they inherit an already-linked UFS from the BootROM (silicon mask ROM, not extractable). The ONLY AP-side re-init that exists is Linux's, and it works.

**SECURE-DMA THEORY REFUTED + THE REAL LEAD IS mclk (2026-08-16, via a custom debug kernel).** Built an instrumented Pixel kernel (repo tree at `/mnt/Harbor/husky-kernel`, `build_shusky.sh` → Kleaf, ~7min build; patched `ufs-exynos.c` pwr_change POST to dump FERROS_UFSP/FERROS_DESC). Booted it (flash the FULL set incl. logical partitions `vendor_dlkm`/`system_dlkm` via `fastboot reboot fastboot`, else it boot-loops), read via `adb bugreport` (dumpstate; shell can't dmesg). Linux's WORKING UFS:
- `WSECURITY=0` (write path "secure") — SAME as ferros saw — yet `utrdl_dma=0x87570000` (LOW non-secure DRAM) and it works. So a secure-marked write DOES reach non-secure memory. **Secure-DMA/GSA theory is DEAD.** No secure-world cooperation needed.
- **`mclk: 178000000`** — Linux calibrates the M-PHY for a 178 MHz UNIPRO clock. **ferros hardcodes MCLK_RATE=133_333_333** in `ferros_hal/src/ufs_cal.rs`; every derived cal constant (mclk_period, line-reset ticks, unipro_18) is wrong if the real clock is 178 → M-PHY mistuned → DME_LINKSTARTUP fails, device silent. **This is the top lead now.** (Note: ABL programmed DBG_PRD=120 ⇒ 133 MHz, but Linux scales to 178 via ufshcd_scale_clks; ferros inherits ABL's clock, so the fix likely needs BOTH setting the CMU UNIPRO clock to 178 AND calibrating for 178 — match Linux exactly.)

**Progress (overnight 2026-08-16):** mclk FIXED to 178 in `ufs_cal.rs` (commit e03494e) — the clock is already 178 (inherited), so no CMU programming needed. BUT it was NOT sufficient: full_init still fails at DME_LINKSTARTUP (device silent), and the live-link doorbell still won't execute even with ABL's own descriptors. **HIBERN8-EXIT RESUME IS A DEAD END.** Linux's captured FWTRACE does a FRESH full link bring-up (pma 0140 init sequence), NO pre_h8_exit writes — Linux never resumes ABL's hibern8, it re-links from scratch. ferros's DME_HIBERN8_EXIT (even with the ported zuma pre_h8_exit PMA cal + correct IS.UHXS wait) drives UPMCRS to G#101 (PWR_FATAL).
