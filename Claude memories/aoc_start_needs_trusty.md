Every husky sensor (IMU, prox/ALS, IR thermometer, mag, pressure, spectral) sits on the AoC's own I2C/I3C buses and is served by Google's AoC firmware through USF (FlatBuffers on /dev/acd-com.google.usf). Owner chose "no TEE, direct if possible" on 2026-10-23.

**Decisive 2026-10-23: both no-TEE routes are exhausted.** (1) Direct buses: inside the AoC block the AP reads only the DesignWare GPIO's pin levels; controllers, SRAM, PCU, pin mux abort, EL3's privileged read refuses — firewalled. (2) Firmware route: GSA's NS mailbox (G#1649_0000) loads+authenticates the vault's aoc.bin (cmd 90) in 30 ms and ferros enables the AoC SYSMMU from the firmware's own IOMMU table (no fault), but the firmware never comes online. The oracle proves why: Linux sends mailbox cmd 90 once and NEVER cmd 91 — it starts the AoC over Trusty (com.android.trusty.gsa.hwmgr.aoc), not the mailbox. ferros's mailbox cmd 91 is accepted (state loaded→4, release→2) but does not run the firmware. So starting the AoC genuinely needs a Trusty client (FF-A + trusty-virtio + tipc).

**How to apply:** full detail in ferros SENSORS.md ("The direct route, measured", "Starting the AoC through GSA's mailbox"); oracle log local at /mnt/Harbor/tmp/aoc-oracle-2026-10-23. Root on husky = Magisk in slot b's init_boot: never leave slot a active after a capture. A second phone (Pixel 3a) shares the dev host's adb — address the husky by serial ([[husky_cold_slot_b]]).

**Trusty client built 2026-10-24 (ffa.rs, trusty.rs, `diag trusty aoc`) — blocked at tipc GO_ONLINE.** Every layer works on hardware: FF-A (request 1.0 to match the 1.0 MTD), MEM_SHARE (Trusty reads+writes our shared pages), API 5, sched-share, GET_DESCR, tipc vdev + vrings + buffers, VDEV_RESET, VIRTIO_START=0. Non-obvious fix from an hv SMC oracle of Android's bring-up (/mnt/Harbor/tmp/trusty-smc-2026-10-24): the queue kick is SMC_SC_NOP(0x32000019, vdev, vring), never the direct KICK_VQ (−7 at API 5). Still no GO_ONLINE; the cause is in Trusty's secure-side virtio/tipc start, not in any local tree. Next: fetch AOSP external/trusty lib/virtio for this TEE build. Testing trap: warm reloads leak FF-A shares (MEM_SHARE → −2), so every Trusty test needs a cold boot; husky-cold.sh hangs if the phone is already in fastboot — flash the gate image and `fastboot reboot` by hand.

**SOLVED 2026-10-24: the AoC runs under ferros.** Blocker was the vdev status byte: AOSP Trusty's tipc probe (trusty-lk lib/trusty/tipc_virtio_dev.c validate_descr) wants exactly 0x07 (ACK|DRIVER|DRIVER_OK), not 0x0F, and virtio_start swallows the probe error (returns 0). Sequence: `diag aoc boot` (load only, GSA state 1) then `diag trusty aoc` → GSA state 2, control block magic G#A0C00A0C, 94 services, com.google.usf = service 1. Lesson: when a vendor return code says success but nothing happens, read the secure-side source — AOSP trusty/lk/trusty is public (cloned at /mnt/Harbor/ferros-ref/trusty-lk). Next: aoc_ipc service rings, then USF.

**USF transport works end to end 2026-10-24.** Beyond starting the AoC: ferros drives its IPC rings (aoc_ipc) directly — diag aoc svc <name> (com.google.usf = queue, mbox 1, 256x1024, DOWN IPC+0x5000 / UP IPC+0x45000, IPC=0x95C00000), diag aoc usf opens a channel ([0,OPEN_CHANNEL,chan] then [chan][payload]), signals via mailbox INTGR0 (1<<(mbox%16), a32 0x15200000), replays the HAL's "get server by UUID" FlatBuffer and the AoC answers 88 bytes, matching Android. Carve-out is Device memory (no cache maintenance). Remaining: the USF FlatBuffer sensor protocol (enumerate/open/subscribe/decode) on top; reference captures in /mnt/Harbor/tmp/usf-captures-2026-10-23, decode with tools/usf-decode.py.

**Sensors stream under ferros, 2026-10-24 (commits 034b502, 8a51905).** Three things were missing beyond the transport: (1) the sensor rails LDO7S/LDO5S on the sub PMIC are left OFF by ABL — turn on (bit 7, regs G#35/G#33) before the firmware loads; (2) a fresh AoC registry holds only `log` and lists zero sensors — the AP must push every `.reg` script (vendor registry, append/, persist factory calibration) as LoadScript type 24 to the registry server with the board CDT (from ABL DT /chosen/plat = G#26100), then Set "/" loaded=1; with CDT 0 the AoC silently skips husky_common/dvt; (3) messages >1012 bytes go as kind-3 fragments. Protocol decoded from the factory image's sensors.usf.so/libusf.so (factory zip at /mnt/Harbor/tmp/husky-factory). Scripts live on Harbor /mnt/Harbor/firmware/husky-aoc (never the repo), vault via tools/husky-aoc-reg.sh. Full write-up in SENSORS.md "The sensors from cold". Lesson: when a vendor service answers but has nothing, look for AP-side configuration the vendor userspace pushes (the HAL skips the push when the registry says loaded, so a HAL-restart capture never shows it).

**Front TMD3719 (prox + ALS) needs the display, 2026-10-24 (7da2fcc):** panel TE2 must be programmed (ABL leaves it off; display does it with brightness + after display on) AND the AoC must get a type-1001 DisplayInfo message (DBV, on, 120 Hz, op 120). Without them: "Sync delay shouldn't be less than 0" + TMD3719 watchdog status 0. Prox samples are 15 floats incl. raw photodiode counts (not a bool). `diag aoc log` reads the AoC firmware's own log — first stop when a sensor is silent.
