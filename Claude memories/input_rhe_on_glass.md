The owner is going over the text-input idea for the phone (the input device the attest screen and `ahau` wait on). The proposal: rhe on glass — four primary buttons, one per finger; each takes a tap or a swipe up/down/left/right, so five per finger, twenty single gestures; chords across fingers multiply that.

rhe (/mnt/Harbor/Code/rhe): a phonetic chord engine — 9 keys, left hand chords vowels, right hand chords consonants with the thumb as the voicing bit; you type sounds and a 135k-word pronunciation dictionary spells the word; ordered briefs split homophones by which finger lands first; gestures effort-ranked on real hands and assigned by frequency; number and symbol modes.

How it maps onto the touch server (payloads/touch: per-contact id, phase down/move/up, pressure, x, y; CHANGES returns events oldest-first):
- commit on lift — the gesture is first-down to last-up (rhe's "keys never all hit zero until the roll completes");
- tap vs swipe by distance travelled, never by time — keeps the no-time-windowed-gestures rule ([[feedback_no_animations]]);
- swipe direction can replace rhe's thumb voicing bit; first-down order gives ordered briefs for free;
- effort: flex/extend (up/down) is cheap, sideways is costly, ring finger worst — measure and rank before assigning;
- 4 buttons × {tap, up, down} = 12 = a dozenal digit set in single gestures.

Catch for attest: rhe's phonetic engine spells via a dictionary, but the handle must be exact bytes (a handle may not be a word; one wrong byte derives a different identity) — attest needs a literal mode, not the phoneme engine. Gestures without visible letters resist shoulder-surfing, which suits a secret.

**Owner: prioritise single-finger interaction** (2026-10-27; grip unknown). That makes grip irrelevant (thumb one-handed or index two-handed) but drops chords, so a stroke's meaning is (start zone) × (direction). 4 zones × (tap + 4 swipes) = 20 is too few for letters + digits; recommended: add diagonals, tap + 8 directions = 9 per zone, 4 zones = 36 = exactly 0-9 + a-z, ferros's base36 alphabet. Effort-rank all 36 on real hands (diagonals cost more), cheapest to most frequent. Chords become an optional speed layer later, never required. Handles need **spaces and capitals**: the handle guard already handles multi-word, mixed-case handles and treats a case change as a different identity — so 0-9 a-z alone is not enough for attest.

Spaces and punctuation (owner liked the 36; asked for spaces, periods etc.): space is the most frequent character in text, so it gets the cheapest stroke. Proposed: a **fifth zone = the space bar**, bottom centre — tap = space; its 8 directions take backspace (left: where delete is expected), period, comma, enter (attest: submit), shift, apostrophe, hyphen, question mark, effort-ranked. **Shift is a stroke before the letter, not a held key**: one shift = next letter capital, two in a row = caps lock (a sequence, not a timed hold). **A symbol page** for the long tail: one stroke opens it, the next stroke on the same four zones picks one of 36 symbols, then it drops back (rhe's symbol mode). Totals: 45 single-stroke characters (36 alphanumerics, space, 8 edits/punctuation), everything else two strokes.

**Direction change (owner, 2026-10-27, later): design for looking, not blind.** Physical keyboards are optimised so you don't have to look because you can feel the keys; glass has nothing to feel, so you look anyway — a blind zone-gesture scheme trades away glass's strength. Owner's lean: a more traditional visible layout, but a **honeycomb** (organic, not tied to a two-hand finger layout), plus a way past spelling every letter. Agreed plan: **shape writing on a honeycomb** — trace one continuous path through a word's letters, commit on lift, a decoder matches the shape to a dictionary word (Swype/Gboard glide). Why hexes: all six neighbours equidistant (cleaner path shapes, uniform targets), fewer bigger keys, and shapes move from traced-by-sight to muscle memory with use. Then an **English optimisation pass** (rhe's frequency × effort method, applied to path shapes; rhe's 135k-word dictionary + frequency list feed the decoder). Attest: **tap** single hexes on the same layout for exact bytes (a handle may not be a dictionary word); a visible keyboard is readable over a shoulder — decide for attest. Starting point for count: alternating rows of 7 and 6 hexes = exactly 26 cells in four rows, ~1 cm keys on the 1344-wide panel (~40% wider than phone QWERTY); space/backspace/enter outside the 26. The earlier zone-stroke idea survives as tap + flick toward one of a hex's six edges if character-by-character input is ever wanted.

**Scrolling extent (owner):** scroll the keyboard down to reveal numbers, then symbols, then emoji, then obscure symbols. Fits the shell's camera-over-one-plane / nothing-moves model: fixed key positions become muscle memory; depth ∝ rarity, so the optimisation pass covers the whole extent. Open decisions: (1) scroll vs word-trace are both drags — **DECIDED (owner): two-finger swipe/scroll**, alternates to be thought on later (owner, after the tap/trace tension: the centre is the most valuable, cheapest-to-reach spot and belongs to frequent letters, and a centre strip split the honeycomb). One finger traces, two fingers scroll — separated by finger count, not position; no timing (a trace begun by the first finger is dropped when the second lands, and nothing commits before lift); the rare action gets the less convenient gesture. Cost: one-handed thumb use can't two-finger drag — a thin one-finger handle on an edge is the fallback if one-handed matters. Keep system two-finger gestures (map zoom, the test app's two-finger tap back) distinct from a keyboard two-finger drag. SUPERSEDED, kept for the record: **the scroll strip in the centre** (reachable equally by either thumb or an index finger, so grip-agnostic; an edge strip favours one hand). A drag's job is decided by where it starts: on the strip it scrolls, on a key it traces, and a trace may cross the strip. The strip costs about one key width per row, so the honeycomb splits into two halves around it — e.g. each half alternating rows of 4 and 3 = 14 cells a side, 28 total (26 letters + 2 spare), keys ~8 mm (still > phone QWERTY's ~7); with two thumbs each owns a half; (2) no animations — scrolling tracks the finger 1:1 and stops on lift, no fling momentum or snap; section jumps instant; (3) fixed positions vs a personal recents row near the top; (4) after picking a symbol: stay put (runs of digits) or jump straight back to letters. **Tap vs trace pull opposite ways on one layout** (owner asked if tap is 'Dvorak-ish'): Dvorak's principle carries (frequent letters in the cheapest spots) but not its arrangement (two hands, home row, finger columns). Hand alternation helps only with two thumbs on the split halves; with one finger, alternating across the centre strip is the longest hop. Tapping wants frequent letters bunched (short hops); tracing wants common words to have distinct shapes (letters spread) — bunched letters make different words trace near-identical paths. Published gesture-keyboard optimisation found the same conflict. So the English pass scores both, with an owner-chosen weight; recommend leaning toward trace accuracy, since tracing is the main word input and tap is mostly exact text (attest).

**Layout: 3 × 11 honeycomb (owner).** Physical keyboards stagger their rows (a typewriter-linkage leftover), which sits much closer to a honeycomb's half-key row offset than to a square grid, so standard layouts drop on with little distortion. 3 rows × 11 = 33 cells = the 26 letters + the punctuation QWERTY/Dvorak keep in their letter rows. A layout becomes data — a mapping onto the 33 cells — so QWERTY, Dvorak (the owner's), Colemak and the custom optimised layout are all options. Trade-off: 11 across in portrait plus the half-key offset ≈ 6 mm hexes (a little under phone QWERTY's ~7 mm, well under the 7-wide honeycomb's ~1 cm) and only ~18 mm tall. Tracing tolerates small keys (the decoder reads shape); tapping exact text (attest) gets harder — recover target size with taller hexes (some cost to equal-neighbour geometry) or landscape (~14 mm). Standard layouts weren't built for tracing, so the optimised one should trace more accurately. **For Dvorak's letters alone, 10 columns suffice** (owner asked): home row uses all 10, bottom 9, top 7 — 26 letters in 30 cells, and the 4 empty cells are exactly where Dvorak keeps ' , . ; (so its punctuation stays in place for free); an 11th column only adds - (and / =). 10 across ≈ 6.6 mm hexes vs ≈ 6.1 mm at 11. A honeycomb offsets every row by the same half key, unlike a physical keyboard's uneven stagger, so letters keep row and column but diagonal neighbours shift slightly.

**How to apply:** lead with shape writing on a honeycomb (the 36-stroke zone scheme is superseded); decide key count + layout with the owner, then the English optimisation pass; tap mode for attest's exact bytes; the scrolling extent with a scroll strip, 1:1 and unanimated.
