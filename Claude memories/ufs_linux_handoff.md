New approach to the [[ufs_husky_wall]]: since ferros's UFS bring-up is register-identical to Linux's yet the device stays silent for ferros (off-chip/analog blocker), **let the Google kernel bring the UFS link up, then jump into ferros without resetting the controller** so ferros adopts the living link. "m1n1 for husky," except the chainloader is a gutted Linux.

**Mechanism (all working as of 2026-08-18):**
- ferros relinked to a 12 MB no-map carveout `ferros_handoff@92400000` (added to `zuma-rmem.dtsi`); shim build via `FERROS_SHIM_HANDOFF=1` (cfg `shim_handoff`, `aarch64-shim.ld`). Its image + stack + static `UFS_BUF` all land in the reserved region, so the UFS master DMAs only into DRAM Linux never mapped.
- Kernel side: `aosp/arch/arm64/kernel/ferros_handoff.c` + `ferros_reset.S` (a self-contained copy of `cpu_soft_restart` — CONFIG_KEXEC_CORE is OFF on this build, so kexec's isn't compiled). Loads `/ferros.bin` from the vendor_kernel_boot initramfs into the carveout, `stop_machine` freezes all CPUs, CPU0 does `ferros_soft_restart(is_hyp_nvhe(), 0x92400000, ...)` — the kexec EL2 re-entry path, MINUS `device_shutdown()` so the UFS link stays live. Lands ferros at EL2, MMU off, which its `_entry` fast path expects.
- Repack `/ferros.bin` into vendor_kernel_boot without a kernel rebuild: `husky-kernel/repack-ferros-vkb.sh <shim.bin>` (unpack VNDRBOOT v4, lz4-legacy ramdisk, cpio inject, mkbootimg). Handoff self-disarms if `/ferros.bin` absent — flash `vendor_kernel_boot.img.orig` to neuter it.

**THE WALL WAS pKVM.** `kvm-arm.mode=protected` (pKVM) was ACTIVE (`pkvm-s2mpu-v9 ... registered with hypervisor` x29 in dmesg) despite CLAUDE.md assuming `fastboot oem pkvm disable` was in effect — it had reset. Protected KVM owns EL2 and intercepts `HVC_SOFT_RESTART`, so the handoff crashed (slow ~168s hang → fastboot fallback). Fix: **`fastboot oem pkvm disable`** (bootloader shows `pKVM is disabled (fastboot=kvm misc=auto)`). After that the handoff lands cleanly — ferros ran its full M0 path and executed a PSCI SYSTEM_RESET from EL2 (fast reboot-logo loop = success signature). Cold ferros boot proved BOOT_EL=2 regardless because ABL→ferros never involves Linux/pKVM; pKVM only cages the Linux→ferros handoff. **Always verify `cat /proc/cmdline | grep kvm-arm.mode` before blaming the handoff.**

**Device constraint learned:** the no-map scratch at `0x92F00000` does NOT survive a reset (even a warm PSCI reset — DRAM decays; `memremap` read/write works fine WITHIN a boot, verified by round-trip). So cross-reboot breadcrumbs are dead. ramoops (`0xfd3ff000`) reportedly does survive (bootloader preserves it) — that's the persistence channel if needed. M1 (UFS read + result reporting) needs a persistence-independent channel: live-observe from CPU0 (freeze CPUs 2-7, ferros on CPU1, CPU0 polls scratch with IRQs off and printks), or ramoops, or framebuffer.

Build: `cd husky-kernel && ./build_shusky.sh --config=use_source_tree_aosp` (source GKI so arch/arm64 changes compile in; ~6 min incremental). Flash boot + vendor_kernel_boot in bootloader-fastboot; dlkm only needs reflash if vermagic changes (same dirty commit = unchanged, old modules still load).

## SOLVED 2026-08-19: ferros READS the flash over the adopted link

The dead doorbell was the **per-command HCI_UTRL_NEXUS_TYPE** (reg_hci+0x40). Exynos `setup_xfer_req` runs before every doorbell: `type |= (1<<tag)` for a SCSI command, `type &= ~(1<<tag)` for a NOP / device-management command. The adopt-path skipped `full_init`, so it never ran this per-command step — and my blanket `0xFFFFFFFF` was actively WRONG for the NOP (nexus bit set when it must be clear), which wedged the transfer engine (vendor_IS bit 19). Fix in `shim::entry_m1`: clear slot-0 nexus before the NOP, set it before the READ, matching the driver exactly.

Result: NOP round-trips (OCS=0, nop_rsp=0x20 NOP IN from device), READ(10) LBA 0 returns OCS=0, GOOD status, residual=0, and the real **GPT protective MBR** (byte 0x1FE = `55 aa`, partition type `0xEE`, start LBA 1, size 0xFFFFFFFF). **ferros read block 0 of the Pixel's UFS over Linux's live link — the UFS wall is broken.**

Result signal caveat: PSCI SYSTEM_OFF (0x84000008) REBOOTS on this Pixel, doesn't power off — so "success = power off" is useless. Use the ramoops dump as the signal. ramoops read is flaky (loop's cold fallback-to-fastboot sometimes wipes it) — retry, or add a one-shot kernel gate (skip handoff if ramoops magic present) for reliability. Disarm cmd must use ABSOLUTE path to vendor_kernel_boot.img.orig (cd into out/shusky/dist first).

**WRITE ALSO VERIFIED (2026-08-19): full UFS block I/O works.** entry_m1 does a data-safe write test on scratch LBA 30_000_000 (4KB blocks; deep in userdata, restored after): read original -> write "FERROSw!"+pattern -> read-back byte-exact (wrote_ok=1) -> restore original -> read-back (restored_ok=1). All commands OCS=0, Android data untouched. read_block + write_block both proven. **The UFS wall is fully broken.** Committed: forge 5d6aa57 (read), 01e3f0c (write).

Test-harness reliability FIXED via a one-shot gate (kernel ferros_handoff.c): postcore ferros_ramoops_read sets `ferros_reported` when it finds+prints a result; ferros_handoff() skips if reported. So: boot1 handoff -> ferros warm-resets -> boot2 reports + boots to Android (handoff skipped), no loop, no disarm dance. Cycle: flash armed boot+vkb -> reboot -> lands on Android after one handoff+report -> `adb shell su -c "dmesg | grep ferros"`. `adb reboot` re-runs. Device geometry: sda, 4096-byte logical blocks, 256GB (62436352 4KB-LBAs), userdata = 4KB-LBA 2449894..62436347.

Next: (1) no_std vault + a UFS-backed `Device` impl (vault is host-file/std only today; `Device` trait = read_at/write_at/flush/capacity -> map to read_block/write_block, 4KB blocks, RMW for sub-block). (2) repartition — carve a ferros partition (shrink userdata; Pixel GPT surgery, riskier than fastboot). (3) genesis. Kernel-side handoff files (ferros_handoff.c/.S, ufshcd_async_scan hook) live in the husky-kernel tree, NOT the ferros repo.

## Dead-doorbell deep-dive (2026-08-18 overnight, ~17 flash cycles) — SOLVED next day, see above

M1 state: ferros adopts the live link (link_up=1, HCS=0x10f, RSR=1 running), rebases UTRLBA onto its carveout UTRD (0x92403400, readback matches), rings UTRLDBR — but the transfer NEVER completes: OCS stays 0xF, DBR bit stuck set, data all zeros. The Exynos vendor DMA engine DOES engage (vs_DMA_state=0x1010101, vs_DMA_dbell nonzero/varying) but raises **HCI_VENDOR_SPECIFIC_IS (reg_hci+0x38) bit 19 (0x80000)** — an UNDOCUMENTED vendor error (the driver never decodes it; not in ufs-vs-regs.h). Bit 20 also set initially, clears when you disable INVALID_UPIU. That persistent bit 19 is the wall.

**CRITICAL tooling fix baked in:** the Exynos vendor registers are at the SEPARATE `reg_hci` block **0x13201100**, NOT `std_base+off`. ferros's `hci_w`/`hci()` use `ufs_cal::base::HCI` (correct). But my M1 diag initially read `UFS_BASE+0xC0` = std region = garbage. Correct reads: vs_FSM=`hci(0xC0)`, DMA_state=`hci(0xC8)`, DMA_dbell=`hci(0xD8)`, VENDOR_IS=`hci(0x38)`, AXI_ctrl=`hci(0xF8)`, NEXUS_TYPE=`hci(0x40)`, INVALID_UPIU_CTRL=`hci(0x10)`/BADDR=`hci(0x14)`, INVALID_UTR/DIN_OFFSET=`hci(0x20/0x24)`. /proc/iomem gives the region bases: std 0x13200000, reg_hci 0x13201100, unipro 0x13204000, **ufsp 0x13208000**, phy 0x13280000, cport 0x132a0000.

RULED OUT as the gate (all measured, not guessed): hibernate (link not in H8); UTRLBA rebase (readback==ferros UTRD); coherency (iocc @ 0x13020710 cleared 0x13→0, no change); S2MPU (0x131F0000 ctrl reads 0 = disabled/bypass per s2mpu-lib.c ENABLE bit); UFSP (0x13208000 regions sctrl=0, disabled); nexus-type (hci 0x40 already 0x7fffffff); IE (0x70ef5, matches Linux); IS clear (fixed: write-back read value, NOT 0xFFFFFFFF — Exynos IS has non-W1C vendor bits); **INVALID_UPIU window (hci 0x10 CTRL already 0, BADDR 0 — the window Linux would use to bound descriptor addresses is DISABLED, so the carveout-out-of-window theory is WRONG).**

So with every address-protection gate OFF, the carveout SHOULD be DMA-reachable, yet the transfer fails with undocumented vendor_IS bit 19. Leading unknowns / next experiments: (1) decode vendor_IS bit 19 from the Exynos/zuma TRM (not in kernel source). (2) Try leaving iocc=3 (coherent) — the frozen stop_machine CPUs keep the coherency domain alive, so coherent DMA may actually be REQUIRED, not harmful. (3) Relocate ferros's UFS_BUF into low/normal memory (link a dedicated section < 0x90000000 where Linux's working descriptors live, e.g. Linux utrdl~0x87xxxxxx, ucdl=0xfc600000) to test if the high carveout address itself is the problem via some undocumented range check. (4) The safe reuse-Linux's-ring test (the earlier hand-built one hung the bus — do it with ferros's tested send_nop pointed at reachable memory, not raw). (5) Compare ferros's UTRD dword layout byte-for-byte against Linux's live UTRD[0] — maybe a descriptor-format field the Exynos engine rejects.

**Test harness reminder:** result signal is PSCI — success (link_up && nop_ocs==0) → SYSTEM_OFF (0x84000008, phone powers OFF, stays off = win); else SYSTEM_RESET (0x84000009, reboot loop → fastboot ~105s). Crash → hang → cold reset → **ramoops WIPED** (only warm PSCI reset preserves it), so a crashing probe self-erases its breadcrumb. ferros's sync-exception handler SKIPS faulting instrs (advances ELR); a bus HANG (wedged MMIO read) is NOT a fault and just hangs. Cycle: flash armed boot+vkb → loop → fastboot → flash vendor_kernel_boot.img.orig (disarm) → boot → `adb shell su -c "dmesg | grep ferros"`. All via `adb reboot bootloader` / fastboot — no buttons needed.
